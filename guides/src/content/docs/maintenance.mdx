Production advice ages fast. A default changes in a minor release, a library moves, a link starts pointing to
the wrong version. A guide that was right last year can quietly turn wrong.

This page shows how we keep that from happening. It is also our own runbook: when we update the guides we follow
these steps and everything they mention is public, from the versions to the test runs.

## Four things that go out of date

| What | How we notice | What we do |
| ---- | ------------- | ---------- |
| Versions | Renovate watches configured package managers and pinned tooling | Tooling updates merge on their own pull request. The versions the guides are written for change together in the baseline. |
| Advice | A tested claim's test fails, a baseline update touches a guide, or someone reports a problem | We fix the guide, or the test, before the change lands. |
| Links to official docs | A check on every change and every Monday | We fix the link or record an exception that expires. |
| The generator preview | Its workflow builds every supported combination | The generated CI checks the build, manifests, images and smoke paths. |

## The baseline: one list of versions

Every guide is written for the **baseline**, a list of exact versions kept in
[`data/versions.yaml`](https://github.com/pyahu/initializer/blob/main/data/versions.yaml).
The active baseline is **{guideData.active}**.

The fixture, the service that proves the guides, runs exactly those versions, and its CI fails when one differs.
A tested claim names a test of that fixture, so a baseline update that breaks a claim cannot land. Git keeps
every earlier baseline.

The [reference docs](/reference/docs/) list the baseline with its official documentation. Frontend packages and
auxiliary tooling have additional exact pins in lockfiles, Dockerfiles and workflows; the generator matrix checks
those combinations.

## Updates we take right away

Some dependencies only run our own tooling: the GitHub Actions in CI, the Go modules of the checks and the
packages that build this site. Renovate opens one pull request per group for their minor and patch updates.
It waits three days after each release, so a broken release has time to be pulled. CI has to pass before the
merge, like any other change.

This is the setup the [build quality guide](/guides/build-quality/) recommends, applied to this repository.

## Updates that wait for the next baseline

Updates to the baseline are different. The fixture runs exactly the versions of the baseline and its CI fails
when they differ. The versions also appear in the guides' text. Bumping one file would leave the rest saying
something else.

So Renovate does not open pull requests for them. It lists them on the
[Dependency Dashboard](https://github.com/pyahu/initializer/issues?q=is%3Aissue%20%22Dependency%20Dashboard%22),
an issue it keeps up to date. The same applies to the Go and Node.js toolchains, which are pinned in several
files at once. We update the baseline when enough has piled up or when one update matters.

**Security fixes do not wait.** Available Renovate vulnerability alerts bypass the ordinary release-age delay.
CI also blocks fixable HIGH/CRITICAL vulnerabilities in built images and runs the frontend npm audit. A baseline
security update needs consistent pins and passing checks before it can ship. Scanning deployed registry digests
on a schedule remains an operational prerequisite for each adopting team.

## Updating the baseline

These are the steps we follow, in order.

1. **Pick the updates** from the Dependency Dashboard. Read the release notes of each one.
2. **Change the pins** in `data/versions.yaml`, with updated versions and image digests. Give the baseline a
   new `id` (`v0.1-b4` after `v0.1-b3`) and set `active` to the same value, so pages and generated projects say
   which list they follow.
3. **Update the services** to the same versions: the fixtures in `fixtures/` and the Initializer's own build
   (`gradle/libs.versions.toml`, the Gradle wrapper and each Dockerfile).
4. **Run both test tracks.** The fixture workflow runs every required test and checks every resolved pin. The
   Start workflow builds and runs all 16 supported project combinations, a monorepo of three verticals and the
   frontend browser tests.
5. **Read the guides of the components that changed.** Fix the text and the version numbers. A measured claim
   keeps the run it was measured in; measure it again if the change could move the numbers.
6. **Check the references.** `guidekit check` fails for every entry whose documentation version no longer
   matches; point those at the new documentation. Entries that are not version-pinned are not compared, so search
   them for the old version numbers too.
7. **Write the release notes** in `data/releases.yaml`: for a team whose project was generated on the previous
   baseline, each step to apply, how to tell whether the project still needs it and how to check the result. We
   apply them to a project generated on the previous baseline and run its CI before we publish.
8. **Regenerate and commit.** Run `go run ./cmd/guidekit generate` and commit the changes with the regenerated
   files: the site, the [Agent Skill](https://github.com/pyahu/initializer/tree/main/skills), `llms.txt`, the
   [release notes](/releases/) and the baseline snapshot come from the same data, so all of them change together.
9. **Update the running generator.** Rebuild and redeploy both images, `start` and `start-web`, so
   [start.pyahu.io](https://start.pyahu.io) generates projects on the new baseline.
10. **Tag the release** on the commit the fixture, Start and Guides workflows passed on. The tag has the baseline's
    name and its [GitHub release](https://github.com/pyahu/initializer/releases) carries the same notes.

Changes to what the generator produces between two baselines are listed as unreleased at the top of the
[release notes](/releases/) from the day they reach start.pyahu.io; CI fails a change to the templates that does
not say so.

## Keeping the advice right

- **Tested claims fail loudly.** Each record in
  [`data/evidence`](https://github.com/pyahu/initializer/tree/main/data/evidence) names a required test of the
  fixture. When the behaviour changes, CI fails and the guide is fixed in the same change.
- **Untested guides say so.** A guide with no tested step carries a Draft label on its page, in the menu and on
  the landing page. Steps without a tested claim rest on the official documentation the guide lists and on
  Pyahu's practice.
- **Steps are retired, not deleted.** A removed guide, step or checklist item gets a record in
  [`data/retired.yaml`](https://github.com/pyahu/initializer/blob/main/data/retired.yaml) and a removed step
  keeps its anchor, so links to it keep working.
- **Someone reports a problem.** [Open an issue](https://github.com/pyahu/initializer/issues); we fix the guide
  or say why it stands.

## Keeping the links alive

Every external link is checked on every change and again every Monday, together with the versions that a BOM
manages. Some official documentation is pinned to a release line, such as Spring Boot 4.2, and follows its
latest patch. The link check verifies that release line; the examples and their evidence stay on the exact
baseline patch until the baseline is updated. A link that is down for a reason we accept gets an exception
with that reason. So does a security
advisory with no fix yet. Every exception expires after at most 30 days, so none of them lasts by accident. They
are in [`data/link-exceptions.yaml`](https://github.com/pyahu/initializer/blob/main/data/link-exceptions.yaml)
and [`data/audit-exceptions.yaml`](https://github.com/pyahu/initializer/blob/main/data/audit-exceptions.yaml).

## The generator

The preview generator is implemented in `services/start/` with its page in `frontends/start-web/`. It supports
hexagonal and DDD layered services, REST, optional PostgreSQL, OIDC and Next.js, and a monorepo of verticals in one
Gradle build, each with its own style and database. Its workflow generates all 16 combinations and runs each
generated project's CI, including strict manifest checks, vulnerability scans and smoke tests, and builds and starts
every vertical of a generated monorepo. The monorepo fixture is what the generator produces for its options. Passing the matrix does not prove every operational recommendation in the guides; the tested claims say
what is proven.

Site publication requires successful Guides and fixture workflows for the relevant source inputs, the two that
prove what the site shows. The publication check rejects pending, failed or superseded candidates. Publishing and operating a customer's
service still requires its real image registry, environment settings, database roles, Secrets and deployment pipeline.

A project you generate is yours from then on. Keep it current with Renovate in your own repository, as the
[build quality guide](/guides/build-quality/) shows. Its `README.md` and `AGENTS.md` name the baseline it was
generated on and link to the [release notes](/releases/) after it: the steps to move it to a newer baseline.
