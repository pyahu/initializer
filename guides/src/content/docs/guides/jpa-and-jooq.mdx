The orders page was fast in review. In production it takes four seconds and the database log shows why: one
query for the orders, then one more for every order on the page. Nobody wrote those queries. The mapping did.

This guide helps you pick between Spring Data JDBC, JPA and jOOQ and then use the one you picked without
surprises: what JPA does behind your back, how to load and write data on purpose and how jOOQ fits a schema
that Liquibase owns. For pools, timeouts and migrations, read [the database guide](/guides/database/) first.

## 1. Spring Data JDBC, JPA or jOOQ: which one fits my service?

**In short:** start with Spring Data JDBC. Pick JPA for rich object graphs you change in place and jOOQ when the
SQL itself is the clearest model.

### What's going on

All three talk to the same PostgreSQL. They differ in how much they hide.

Spring Data JDBC loads and saves a whole aggregate, with no lazy loading and no session in between: what you call
is what runs. JPA, here Hibernate 7.4 (the version Spring Boot 4.1.1 manages), tracks the objects you load and
writes your changes for you. That saves code and costs predictability. jOOQ (3.21 in the Boot BOM) hides nothing:
you write SQL in Java, checked by the compiler against your real schema.

Think of it as a car. Spring Data JDBC is a manual gearbox, JPA is an automatic with a mind of its own and jOOQ
is driving on a map you drew yourself.

### Do this

1. Keep Spring Data JDBC, the default in these guides, unless you hit a reason below.
2. Choose JPA when the domain is a graph of objects that change together and you will learn its rules (steps 2
   to 7).
3. Choose jOOQ for reporting, complex joins, window functions or bulk updates, where SQL says it best.
4. Whatever you choose, keep the domain free of persistence annotations: map rows to domain objects in the
   persistence adapter, as [the architecture guide](/guides/architecture/) shows.

### When this is not for you

- A team that already runs JPA well: keep it. Switching tools is a cost too.
- Mixing is fine: JPA or JDBC for writes and jOOQ for heavy reads in the same service share one data source and
  one transaction.

## 2. What does JPA do behind my back?

**In short:** it keeps every entity you load in memory and writes your changes when the transaction commits.
Know when that happens and never let it touch the schema.

```yaml
spring.jpa.hibernate.ddl-auto: validate
```

### What's going on

Inside a transaction, JPA keeps a persistence context: every entity you loaded, plus a snapshot of how it looked.
When you change a field, no SQL runs. At commit, Hibernate flushes: it compares each entity with its snapshot and
sends an UPDATE for what changed. This is dirty checking.

So a setter called by mistake becomes a database write and a query in the middle of a transaction can trigger a
flush first, so the query sees your pending changes.

The schema is the other surprise. Hibernate can create and change tables itself. With Liquibase in charge, that
must stay off. Spring Boot 4.1.1 defaults `ddl-auto` to `none` unless the database is embedded.

### Do this

1. Let Liquibase own the schema ([database guide, step 5](/guides/database/#db-migrations)).
2. Set `spring.jpa.hibernate.ddl-auto: validate`, so the app fails at startup when entities and tables disagree.
3. Change entities only inside a transaction that means to write them; mark read paths
   `@Transactional(readOnly = true)`.
4. Keep `spring.jpa.show-sql` off in production; log slow queries instead (step 3).

### When this is not for you

- Spring Data JDBC and jOOQ have no persistence context: every write is a call you make.

<a id="orm-n-plus-one"></a>

## 3. Why does one page run a hundred queries?

**In short:** a lazy association loaded inside a loop runs one query per row. Decide what the page needs and
load it in one query.

### What's going on

When an order has a list of lines, JPA can load the lines later, on first access. That is lazy loading. It is
right as a default but in a loop over 100 orders, each `order.getLines()` runs its own SELECT: 1 query for the
orders plus 100 for the lines. That is the N+1 trap.

The opposite default is worse. In JPA, `@ManyToOne` and `@OneToOne` are eager unless you say otherwise, so every
query loads them, needed or not, often with extra selects of their own.

### Do this

1. Mark every association `fetch = FetchType.LAZY`, including `@ManyToOne` and `@OneToOne`.
2. Load what a use case needs on purpose: a `JOIN FETCH` query or an `@EntityGraph` on the Spring Data repository
   method.
3. As a safety net, set `spring.jpa.properties.hibernate.default_batch_fetch_size`, so forgotten lazy loads go
   in batches instead of one by one.
4. Set `spring.jpa.properties.hibernate.query.fail_on_pagination_over_collection_fetch: true`: paging over a
   fetched collection then fails instead of loading the whole table into memory.
5. Turn on `spring.jpa.properties.hibernate.log_slow_query` with a millisecond threshold, so slow queries reach
   the log.

### When this is not for you

- `JOIN FETCH` works well for one collection per query. For two collections, use two queries or a projection.

<a id="orm-open-in-view"></a>

## 4. Why do queries run after my controller returns?

**In short:** Spring Boot keeps the JPA session open for the whole web request by default. Turn that off.

```yaml
spring.jpa.open-in-view: false
```

### What's going on

`spring.jpa.open-in-view` is `true` by default in Spring Boot 4.1.1. It binds one entity manager to the request,
so lazy associations still load while the response is written, outside your transaction and after your service
code is done. Boot even logs a warning about it at startup.

It hides N+1 queries in serialization, holds a database connection longer than needed and makes it unclear
which code touches the database.

### Do this

1. Set `spring.jpa.open-in-view: false`.
2. Load everything a response needs inside the service transaction (step 3) or return a projection (step 5).
3. If a `LazyInitializationException` appears, fix the fetch plan. Do not turn the setting back on.

### When this is not for you

- Server rendered pages that walk entity graphs in templates rely on it. Moving to projections is still the fix.

<a id="orm-projections"></a>

## 5. How do I read data without loading entities?

**In short:** for reads, ask for exactly the columns you show, as a projection and skip the persistence context.

### What's going on

An entity is built for change: loaded whole, tracked and checked at flush. A list page that shows three fields
pays for all of that and gets nothing back. The Hibernate guide says it plainly: for use cases that only read, fetch
DTO projections.

A projection is a small class or interface with just the fields you need. The query selects only those columns
and nothing is tracked.

### Do this

1. Return records or interface projections from Spring Data repository methods for list and search pages.
2. Use entities only where you change them.
3. Mark read services `@Transactional(readOnly = true)`.

### When this is not for you

- A screen that edits the same data it shows: load the entity once and change it.

<a id="orm-batching"></a>

## 6. How do I write many rows fast?

**In short:** turn on JDBC batching and use sequence ids, so Hibernate sends inserts in groups instead of one by
one.

```yaml
spring.jpa.properties.hibernate.jdbc.batch_size: 50
spring.jpa.properties.hibernate.order_inserts: true
spring.jpa.properties.hibernate.order_updates: true
```

### What's going on

Batching is off by default in Hibernate 7.4: `hibernate.jdbc.batch_size` is 0. Saving 10,000 rows then means
10,000 round trips.

Ids matter too. With `IDENTITY` ids the database assigns the id on insert, so Hibernate has to run each insert
right away and the Hibernate guide notes this disables batching for inserts. A sequence lets Hibernate get ids
ahead of time and its pooled optimizer hands out a block of ids per database call.

### Do this

1. Set a batch size and turn on ordered inserts and updates, as above.
2. Map ids with `GenerationType.SEQUENCE`, backed by a sequence created in a Liquibase changeset.
3. For very large loads, process in chunks and clear the persistence context between them (step 7).

### When this is not for you

- Bulk changes that touch many rows with one rule: one SQL statement does it better. Use jOOQ or a JDBC query.

<a id="orm-long-transactions"></a>

## 7. What goes wrong in long transactions and entity caches?

**In short:** keep transactions short and leave the second level cache off until you can prove you need it.

### What's going on

The persistence context grows with every entity you load. A job that reads 100,000 rows in one transaction keeps
them all in memory and every flush checks them all. Meanwhile it holds a database connection that other
requests are waiting for.

The second level cache keeps entities between transactions, inside each pod. With several pods, each has its own
copy and a change made by one pod is not seen by the others until their copy expires. Hibernate turns it on only
when you configure a cache provider.

### Do this

1. Keep one transaction per use case and keep remote calls out of it.
2. For batch jobs, work in chunks: flush and clear the persistence context after each chunk.
3. Do not configure a second level cache by default. When reads really need caching, cache explicit results at
   the service level, as the [caching guide](/guides/caching/) shows.

### When this is not for you

- Reference data that almost never changes and is read on every request: a second level cache with a clear
  expiry can work. Measure first.

## 8. How do I use jOOQ with my migrations?

**In short:** run the Liquibase migrations against a real PostgreSQL in a container, then generate the jOOQ
classes from that schema.

### What's going on

jOOQ checks your SQL at compile time against classes generated from the database schema. That only helps if the
schema is the real one, the one Liquibase builds.

jOOQ used to read Liquibase files directly but the jOOQ 3.21 manual deprecates that and recommends running the
migrations in a container with Testcontainers and generating from the result. At runtime, Spring Boot creates a
`DSLContext` that joins Spring transactions, so jOOQ and repository calls in one `@Transactional` method commit
together.

### Do this

1. Add `spring-boot-starter-jooq`; the Boot BOM sets the jOOQ version.
2. In the build, start PostgreSQL with Testcontainers, apply the Liquibase changelog, then run jOOQ's code
   generator with its official Gradle plugin (`org.jooq.jooq-codegen-gradle`).
3. Treat the generated classes as build output, not code you edit.
4. Keep jOOQ in the persistence adapter and map records to domain objects there.
5. Set `spring.jooq.sql-dialect` only if detection fails; Boot detects it from the data source.

### When this is not for you

- Simple create, read, update and delete over aggregates: Spring Data JDBC needs less setup.
- Teams that cannot run Docker in the build: generation from a live database needs it.

## Put it all together

Each choice lands in the build, in `application.yaml` and in the persistence adapter.

### In the build

- `spring-boot-starter-data-jpa` or `spring-boot-starter-jooq`, with versions from the Spring Boot BOM: Hibernate
  7.4.5.Final, Spring Data JPA 4.1.1 and jOOQ 3.21.7 in Spring Boot 4.1.1 (step 1).
- For jOOQ, a generation task that migrates a PostgreSQL container with Liquibase and then generates (step 8).

### In application.yaml, with JPA

- `spring.jpa.hibernate.ddl-auto: validate` (step 2).
- `spring.jpa.open-in-view: false` (step 4).
- `hibernate.default_batch_fetch_size`, `hibernate.query.fail_on_pagination_over_collection_fetch` and
  `hibernate.log_slow_query` under `spring.jpa.properties` (step 3).
- `hibernate.jdbc.batch_size`, `hibernate.order_inserts` and `hibernate.order_updates` under
  `spring.jpa.properties` (step 6).

### In the code

- Lazy associations everywhere and fetch plans per use case (step 3).
- Projections for reads, entities for writes (step 5).
- Sequence ids (step 6), short transactions and chunked jobs (step 7).
- Entities or jOOQ records only inside the persistence adapter, mapped to plain domain objects (step 1).
