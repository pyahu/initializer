The build passes on your laptop and fails in CI. A teammate gets a different Spring version than you. A
`NullPointerException` reaches production from a method everyone was sure never returned null. Half of every code
review is about spaces and imports.

None of this needs discipline, only a build that refuses to go on. This guide sets up a Gradle build for a Spring
Boot service in eight steps: the same tools everywhere, one place for versions and gates that stop bugs, nulls and
drift before anything ships.

## 1. How do I make sure every machine builds the same way?

**In short:** commit the Gradle wrapper with the checksum of its distribution and pin the JDK with a toolchain.

```text
distributionSha256Sum=dce76f55f8e251a3a1f130eb120f30b3d271de2b76c9b0729d316b5a1b6dc01f
```

### What's going on

"Works on my machine" usually means two machines with two different tools. The Gradle wrapper fixes the Gradle
version: `./gradlew` downloads exactly the version named in `gradle/wrapper/gradle-wrapper.properties`, so your
laptop and CI run the same Gradle.

A download can still be swapped on its way to you. With `distributionSha256Sum`, Gradle compares the downloaded
zip with the checksum you committed and fails the build if they differ. The JDK has the same problem and a Java
toolchain in the build file solves it: the build asks for Java 25 instead of using whatever `java` is on the path.

### Do this

1. Generate the wrapper with the version and its published checksum:

   ```sh
   ./gradlew wrapper --gradle-version 9.8.1 --gradle-distribution-sha256-sum <sha256 from gradle.org>
   ```

2. Commit `gradlew`, `gradlew.bat` and the whole `gradle/wrapper` folder.
3. Set `java { toolchain { languageVersion = JavaLanguageVersion.of(25) } }` in `build.gradle.kts`.
4. In CI, always run `./gradlew`, never a Gradle installed on the runner. Run it inside the pinned JDK image, as
   [The container image](/guides/container-image/) does.

### When this is not for you

- The checksum is checked only when Gradle downloads the distribution. A distribution already in the Gradle home
  is trusted as it is.
- On GitHub, the Setup Gradle action also checks that `gradle-wrapper.jar` itself was not tampered with. Elsewhere,
  check the jar's checksum by hand when it changes.

<a id="bld-version-catalog"></a>

## 2. Where should dependency versions live?

**In short:** in one file, `gradle/libs.versions.toml`. Repositories go only in `settings.gradle.kts`.

### What's going on

When versions are typed into the build file, the same library ends up with two versions in two places and nobody
knows which one won. A version catalog is a single table of libraries, plugins and their versions. Gradle reads
`gradle/libs.versions.toml` and gives the build safe names such as `libs.spring.boot.dependencies`, so a typo is a
build error instead of a silent new dependency.

Repositories have the same problem. If any module can add its own repository, a library can come from somewhere
nobody reviewed. `repositoriesMode = RepositoriesMode.FAIL_ON_PROJECT_REPOS` in settings makes a repository declared
in a project a build error.

### Do this

1. Put every version and plugin version in `[versions]` and refer to them with `version.ref`.
2. Write libraries without a version when a BOM manages them (step 3).
3. Declare `mavenCentral()` and the plugin portal in `settings.gradle.kts` only, with `FAIL_ON_PROJECT_REPOS`.
4. Apply plugins with `alias(libs.plugins.x)`.

### When this is not for you

- A build with several modules shares more than versions: build logic goes into convention plugins, covered in
  the monorepo guide.

<a id="bld-boms"></a>

## 3. How do I use Spring Boot's versions without the extra plugin?

**In short:** import Spring Boot's BOM with `platform()` and skip the `io.spring.dependency-management` plugin.

```kotlin
implementation(platform(libs.spring.boot.dependencies))
```

### What's going on

Spring Boot picks versions for hundreds of libraries that work together and publishes them as a BOM, a list of
versions. You want that list, not your own guesses.

There are two ways to use it. The `io.spring.dependency-management` plugin brings it in automatically and lets you
change a version through a property. Gradle's own `platform()` does the same job natively and the Spring Boot
docs say it will likely give you faster builds. The catch: a platform only constrains the configuration it is
declared in and the ones that extend it. That is why the build declares it for `implementation`,
`testImplementation` and `testRuntimeOnly`.

### Do this

1. Add `platform(...)` for each BOM you use: Spring Boot and others such as Spring Modulith and jMolecules.
2. Repeat it in every configuration that resolves dependencies without extending `implementation`.
3. Leave versions off every library the BOM manages.
4. Need a different version of one library? Use a Gradle resolution strategy, not a property: the properties only
   work with the dependency management plugin.

### When this is not for you

- You override many managed versions through properties today: the dependency management plugin keeps that
  simpler, at the cost of build speed.

<a id="bld-error-prone"></a>

## 4. How do I catch bugs before the code runs?

**In short:** run Error Prone inside `javac`, so known bug patterns become compile errors.

### What's going on

Some bugs have a shape: throwing away the result of a call that must be used, a `switch` on an enum that misses a
value, an object of the wrong type passed to `contains` on a collection. Error Prone is a compiler plugin from Google that knows hundreds of these shapes.
It runs while `javac` compiles, so the bug never reaches a test, let alone production.

Think of the whole build as a line of gates. Each one stops a different kind of mistake and the first one that
fails stops the build.

<BuildGatesDiagram />
<DiagramLegend items={['recommended', 'context', 'failure']} />

### Do this

1. Apply the `net.ltgt.errorprone` Gradle plugin and add `error_prone_core` to the `errorprone` configuration.
2. Set `disableWarningsInGeneratedCode = true`, so generated code does not drown your own warnings.
3. Keep it on for main code. The build in this repository turns it off for test code, a deliberate choice to
   keep tests quick to write.
4. Run it on JDK 21 or later: Error Prone 2.43 and newer need it.

### When this is not for you

- An existing codebase with thousands of findings: start with errors only and fix warnings module by module,
  instead of turning everything on at once.

<a id="bld-nullaway"></a>

## 5. How do I stop a NullPointerException at compile time?

**In short:** mark packages `@NullMarked` with JSpecify and let NullAway fail the build on a possible null.

```java
@NullMarked
package io.pyahu.fixture.hexagonal;
```

### What's going on

In Java any reference can be null and the compiler never asks. JSpecify gives you a way to say it: inside a
`@NullMarked` package, every type is non-null unless you write `@Nullable`. NullAway, an Error Prone check from
Uber, then reads those annotations and refuses to compile code that could pass or return a null where none is
allowed.

There is one trap. `@NullMarked` on a package does not cover its subpackages and with `OnlyNullMarked` NullAway
checks nothing outside marked code. A new package without its own `package-info.java` is silently unchecked.

### Do this

1. Add `org.jspecify:jspecify` (the Boot BOM manages it) and `nullaway` to the `errorprone` configuration.
2. Configure NullAway as an error, with `NullAway:OnlyNullMarked=true` and `NullAway:JSpecifyMode=true`.
3. Give every package a `package-info.java` with `@NullMarked`.
4. Write `@Nullable` only where a null is a real answer, such as "not found".

### When this is not for you

- JSpecify mode is still being developed and can report false positives, mostly with generics. Suppress them one
  by one, never for a whole class.
- To catch packages without the annotation, NullAway ships a `RequireExplicitNullMarking` check, off by default.

<a id="bld-format"></a>

## 6. How do I end formatting debates in code review?

**In short:** let Spotless format the code with palantir-java-format and fail the build when it is not formatted.

### What's going on

Spaces, line breaks and import order are not worth a review comment, yet they fill review threads. Spotless takes
the decision away from people: `./gradlew spotlessApply` rewrites the code in one fixed style and
`spotlessCheck` fails when a file does not match. By default `spotlessCheck` is part of `check`, so it runs on every
`./gradlew build`.

### Do this

1. Apply the `com.diffplug.spotless` plugin.
2. Use `palantirJavaFormat(...)` with the version from the catalog, plus `removeUnusedImports()`,
   `trimTrailingWhitespace()` and `endWithNewline()`.
3. Run `./gradlew spotlessApply` before you push or from a pre-commit hook.
4. Keep the formatter version pinned: a new version can reformat lines and that belongs in its own commit.

### When this is not for you

- A large codebase adopting Spotless late: format everything in one commit that does nothing else, so history
  stays readable. Spotless can also format only the files changed since a branch (`ratchetFrom`).

<a id="bld-sbom"></a>

## 7. How do I know which libraries the service ships?

**In short:** make the build write a CycloneDX SBOM next to the jar.

### What's going on

When a vulnerability is announced in a library, the first question is "do we use it and which version?". An
SBOM, a software bill of materials, answers it: a file that lists every library in the build with its version.
The CycloneDX Gradle plugin writes it from the resolved dependencies, so it lists what you actually ship, not what
you think you declared.

### Do this

1. Apply the `org.cyclonedx.bom` plugin.
2. Point `cyclonedxBom` at a fixed path such as `build/sbom/bom.json`.
3. Make `build` depend on `cyclonedxBom`, so every build writes it.
4. Keep the SBOM with the image it describes. [The container image](/guides/container-image/) covers attaching it
   and scanning it.

### When this is not for you

- A build with several modules: in plugin 3.x, `cyclonedxBom` writes one combined SBOM for the project where the
  plugin is applied and `cyclonedxDirectBom` writes one per module.

<a id="bld-updates"></a>

## 8. How do I keep dependencies current without breaking the build?

**In short:** let Renovate open small update pull requests, wait a few days after each release and merge only on
green CI.

### What's going on

Dependencies age quietly. Skip updates for a year and the jump to current versions becomes a project of its own,
usually started by a security advisory on a Friday. Small updates, often, are cheap: one library, one pull request,
one CI run that says whether it still works.

Renovate reads `libs.versions.toml` and the wrapper properties and opens a pull request for each update. Waiting a
few days before proposing a new release (`minimumReleaseAge`) means a broken or withdrawn release is usually gone
before it reaches you.

### Do this

1. Add a `renovate.json` that extends `config:recommended`.
2. Set `minimumReleaseAge`, for example to 7 days.
3. Group libraries that must move together into one pull request, with a `groupName` in a package rule.
4. Require the full build, gates included, to pass before merge.

### When this is not for you

- Some libraries must move as a set: the OpenTelemetry Logback appender, for example, has to match the SDK that
  Spring Boot manages ([Observability](/guides/observability/), step 3). Group them or Renovate proposes a version
  that does not fit.
