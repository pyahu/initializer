Every check is green and the release still breaks. The tests ran on a different JDK than the image, the image itself
was never started and a popular action changed overnight because its tag now points somewhere else. CI said yes to
something nobody actually tested.

This guide builds a GitHub Actions pipeline that proves one more thing at each stage: the code that runs, the build,
the image, the image running and finally where it came from. It stays fast and keeps itself up to date.

<a id="ci-pin-actions"></a>

## 1. Can an action I use change under me?

**In short:** yes, if you use it by tag. Pin every action to a full commit SHA and keep the version in a comment.

```yaml
- uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
```

### What's going on

`uses: some-org/some-action@v4` does not name code. It names a tag and a tag is a label that whoever controls the
repository can move. If a maintainer's account is taken over and the tag is moved, your next run executes new code
with your token and your secrets.

A commit SHA is different: it is a fingerprint of the content. To slip other code in under the same SHA, an attacker
would need a SHA-1 collision. That is why GitHub's security guidance says to pin actions to a full length commit SHA.

GitHub now goes one step further with workflow dependency lockfiles, in public preview: a `.github/workflows/actions.lock`
file, generated by the `gh actions-lock` extension, records the commit behind every action, including the actions
your actions use and checks the identity of the source repository at run time.

### Do this

1. Replace every `@v4` style reference with the full 40 character SHA of that release.
2. Keep the version in a comment after it, so reviews and update tools can read it.
3. Do the same for reusable workflows you call.
4. Let Renovate move the SHAs for you (step 8).

### When this is not for you

- Your repository adopts the lockfile: it pins every action, including the ones your actions call, so SHAs in the
  workflow files are no longer needed. It is still in public preview.
- It always applies otherwise, including to GitHub's own `actions/*`. Pinning costs nothing.

<a id="ci-permissions"></a>

## 2. What should the workflow token be allowed to do?

**In short:** read only by default. Each job asks for the few write permissions it needs.

```yaml
permissions:
  contents: read
```

### What's going on

Every job gets a `GITHUB_TOKEN` and every step in the job can use it, including third party actions. If the token can
write to the repository, so can any action you pull in.

The `permissions` key fixes this. As soon as you name one permission, every permission you did not name becomes
`none`. So `contents: read` at the top of a workflow leaves the token able to read the code and nothing else.

### Do this

1. Put `permissions: contents: read` at the top of every workflow.
2. Grant more at the job level, only where needed. A job that publishes an image with an attestation needs
   `packages: write`, `id-token: write` and `attestations: write` (step 6).
3. Set the default token permission for the repository or organization to read only.
4. Never check out and run pull request code from a `pull_request_target` or `workflow_run` workflow that holds secrets.

### When this is not for you

- A job that only builds and tests never needs write access. If it asks for it, find out why.
- To push to a cloud registry, prefer OpenID Connect (`id-token: write`) and short lived credentials over a password
  stored as a secret.

<a id="ci-pinned-jdk"></a>

## 3. Which JDK does CI build with?

**In short:** the same pinned JDK image the Dockerfile builds with, by digest, so tests and production run the same
bits.

```sh
docker run --rm -v "$PWD/fixtures/single-hexagonal:/w" -w /w "$JDK_IMAGE" ./gradlew --no-daemon build
```

### What's going on

A setup action on a runner installs whatever JDK patch is current that day. The image may be built with another one.
Then the tests pass on one JDK while production runs a different one and anything tied to the exact JDK build, such
as the [AOT cache](/guides/jvm-in-containers/#jvm-aot-cache), behaves differently.

Running Gradle inside the pinned JDK image removes the gap. The image digest names one exact JDK build, the same one
the Dockerfile's build stage uses.

### Do this

1. Put the JDK image digest in one variable at the top of the workflow, such as `JDK_IMAGE`.
2. Run the Gradle build inside that image, as above.
3. Use the same digest in the Dockerfile's build stage.
4. Keep the Gradle wrapper's `distributionSha256Sum`, so a changed Gradle download fails the build.
5. Before using any other tool in the job, check its version, as this repository does for Go.

### When this is not for you

- A library that must work on several JDKs: test them with a matrix instead, since there is no single production JDK.
- The cost: the build runs in a fresh container, so the Gradle cache is not reused between runs here. Step 4 shows
  what caching would take.

<a id="ci-cache"></a>

## 4. How do I cache without trusting other branches?

**In short:** cache downloads, key them by the lock files, keep secrets out and let only trusted runs write to the
cache.

### What's going on

A cache is like a shared fridge: anyone who can open it can eat what is inside or leave something behind. GitHub draws
lines around it. A run can restore caches from its own branch and the default branch and a pull request run also from
its base branch. It cannot read caches of sibling or child branches and caches a pull request creates stay with that
pull request.

The default branch matters most, because every branch can read it. So only some triggers, such as `push`,
`workflow_dispatch` and `schedule`, may write there. Other triggers that resolve to the default branch only get read
access. Without that rule, one bad run could poison a cache that a later, more trusted run restores. And cache
contents are not signed: anyone who can open a pull request can read the base branch's caches.

### Do this

1. Cache dependency downloads with the cache your setup action offers, such as `setup-go` with `cache: true`.
2. Key caches by the hash of your lock or version files, so a changed dependency makes a new cache.
3. Never write tokens, credentials or secrets to a cached path.
4. Let caches be written only by runs on trusted triggers, such as a push to the default branch.

### When this is not for you

- The build is already fast enough: skip the cache. Each one is something to reason about.
- GitHub removes caches not used for 7 days and keeps 10 GB per repository by default, so a cache can always miss.
  Never depend on it for correctness.

<a id="ci-test-order"></a>

## 5. What must pass before an image is published?

**In short:** the code's tests, then the image build, then tests that start that image. Publish only when all three
pass.

### What's going on

Unit and architecture tests prove the code. They do not prove the image starts as a user other than root on a read
only disk, finds its AOT cache or answers its probes. Those things live in the image, so something has to start the
image and look at it from outside.

This repository works that way: the Gradle build runs the unit and architecture tests, `docker buildx build --load`
builds the image and Go acceptance tests start that exact image and check it from outside.

### Do this

1. Run the Gradle build: compile, unit and architecture tests (see [Testing](/guides/testing/)).
2. Build the image from the same Dockerfile production uses and load it locally.
3. Run behaviour tests against that image: start it, call it and check what it does.
4. Upload test reports with `if: always()`, so a red run still explains itself.
5. Make the publishing job depend on the test job with `needs:`, so a failure stops it.

### When this is not for you

- A library or a batch job that ships no image: stop after step 1.

<a id="ci-publish"></a>

## 6. How do I publish an image others can verify?

**In short:** push the image, keep its digest and attach provenance, an SBOM and a signature to that digest.

### What's going on

A tag such as `:1.4` can be moved, so deploy and verify by digest, which names the exact content. Then answer the
question others will ask: who built this, from which commit, with which workflow?

GitHub artifact attestations answer it. The `actions/attest` action writes signed provenance for the digest, using
Sigstore behind the scenes. GitHub documents that this alone gives SLSA Build Level 2; moving the build into a
reusable workflow shared across repositories is how it reaches Build Level 3. The same action can attach an SBOM.
Cosign can also sign the image directly, without keys to store, using the workflow's OpenID Connect identity.

### Do this

1. Push with `docker buildx build --push` and record the digest, for example with `--metadata-file`.
2. Give the publishing job `id-token: write`, `contents: read`, `attestations: write` and `packages: write`.
3. Add `actions/attest` with `subject-name` set to the image name without a tag, `subject-digest` set to the digest
   and `push-to-registry: true`.
4. Attach the SBOM too (`sbom-path`), generated by Syft 1.54.1 or the CycloneDX build plugin.
5. Check it before deploying: `gh attestation verify oci://<image>:<tag> -R <owner>/<repo>`.

### When this is not for you

- You sign with Cosign 3.1.3 instead: `cosign sign <image>@<digest>` in the same job, with `id-token: write`. Details are
  in [The container image](/guides/container-image/).
- Pull requests should not publish anything. Run this job only for the default branch.

<a id="ci-fast"></a>

## 7. How do I keep the pipeline fast?

**In short:** run only the workflows a change can affect, cancel runs nobody needs anymore and cap every job's time.

```yaml
concurrency:
  group: fixture-single-hexagonal-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

### What's going on

When every push runs everything, the queue grows and people stop waiting for CI. Three settings fix most of it. A
`paths` filter skips a workflow when nothing it reads changed. A `concurrency` group lets a new push cancel the run
it replaces. And `timeout-minutes` stops a stuck job: the default is 360 minutes.

One trap: a workflow skipped by a path filter leaves its checks "Pending". If that check is required, the pull
request cannot merge.

### Do this

1. List in `paths` everything the workflow reads, including the workflow file itself.
2. Add a `concurrency` group per workflow and ref and cancel in progress on pull requests.
3. Set `timeout-minutes` on every job, close to its normal duration.
4. Do not make a path filtered workflow a required check.

### When this is not for you

- Runs on the default branch that produce something later runs read, such as a test report: let them finish. This
  repository cancels only pull request runs for that reason.

<a id="ci-renovate"></a>

## 8. Who keeps the pipeline itself up to date?

**In short:** Renovate. It opens pull requests for action SHAs, images and libraries and CI tests each one.

```json
{
  "extends": ["config:recommended", "helpers:pinGitHubActionDigests"],
  "minimumReleaseAge": "7 days"
}
```

### What's going on

Pins do not update themselves. A pinned action, image or library slowly falls behind and misses security fixes,
until someone updates everything at once and something breaks.

Renovate reads your workflows, Dockerfiles and Gradle files and opens one pull request per update. The
`helpers:pinGitHubActionDigests` preset pins actions to digests. `minimumReleaseAge` makes it wait before proposing a
new release, which gives a broken or malicious release time to be pulled.

### Do this

1. Add a Renovate configuration that extends `config:recommended` and `helpers:pinGitHubActionDigests`.
2. Set `minimumReleaseAge` to a few days.
3. Require CI to pass before an update merges.
4. Group updates that must move together, such as a BOM and its plugin.

### When this is not for you

- You prefer Dependabot, GitHub's built in alternative. It also updates actions and the lockfile from step 1 supports
  it.

## Put it all together

This repository's fixture workflow does steps 1 to 5 on every push; publishing (step 6) is the part it does not do yet.

### The top of the workflow

Read only permissions, a concurrency group and the pinned JDK in one place (steps 2, 3 and 7), as they appear in
`.github/workflows/fixture-single-hexagonal.yml`.

```yaml
permissions:
  contents: read

concurrency:
  group: fixture-single-hexagonal-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

env:
  GOTOOLCHAIN: go1.27.2
  # temurin-jdk-image of baseline v0.1-b1.
  JDK_IMAGE: eclipse-temurin@sha256:a75cd2f1bd3e1e45da898bf658f1f1039ab7392b34844862514d230fd6a516d4
```

### The build stages

The steps of the same job in order (steps 3 and 5): build in the pinned JDK, build the image, test the image and
always keep the report.

```yaml
- name: Gradle build in the pinned JDK
  id: gradle
  run: docker run --rm -v "$PWD/fixtures/single-hexagonal:/w" -w /w "$JDK_IMAGE" ./gradlew --no-daemon build
- name: Image
  id: image
  run: docker buildx build --load -t single-hexagonal:ci fixtures/single-hexagonal
- name: Acceptance
  id: acceptance
  run: |
    mkdir -p out
    go test -tags acceptance -count=1 -p 1 -json ./acceptance/... > out/acceptance.json
```

### The Gradle download

The wrapper checks the Gradle distribution against a hash, so CI never builds with a Gradle it did not expect (step 3).

**Check it:** change one character of the hash and run `GRADLE_USER_HOME=$(mktemp -d) ./gradlew --version`. The build fails on the checksum. Gradle only checks it while downloading, hence the empty Gradle home.

### What to add for publishing

- A second job with `needs:` on the test job, running only on the default branch (step 5).
- Job permissions `id-token: write`, `contents: read`, `attestations: write` and `packages: write` (step 2).
- Push by digest, then `actions/attest` for provenance and the SBOM (step 6).
- A Renovate configuration with pinned action digests and a minimum release age (step 8).
