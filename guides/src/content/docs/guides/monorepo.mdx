Your team owns five services, so you put them in one repository. A year later, a change in billing breaks the
orders build, every pull request waits for every test, a CI file lists forty paths nobody dares to touch and
nobody can release orders without a billing fix going out with it. You built one big service with five
deployments.

This guide keeps what one repository is good at (one build, one version of every library, a contract and its
consumers changed in one pull request) while each service keeps its own code, contract, database, image and
release. The build itself enforces the boundaries, so they hold when nobody is looking.

<a id="mono-when"></a>

## 1. Should our services share one repository?

**In short:** yes, when one team, or a few teams that work closely, own the services and often change two of them
together. First check that you need several services at all.

### What's going on

A shared repository is like a shared office. Working side by side makes small changes across services cheap: rename
a field in a contract and fix its consumer in the same pull request. But the office only works if everyone keeps
their own desk. When services start reading each other's code, the office turns into one big room where nobody can
move anything alone.

The repository is not the problem. Coupling is: dependencies that force services to change and release together.
Separate repositories make coupling expensive by accident. One repository makes it free, so it needs rules that the
build checks (steps 3 and 4).

Before you split, ask why the parts are separate services. If they share a database, release together and are
owned by one team, a single service with well-kept modules is simpler and faster to change (see
[Architecture](/guides/architecture/)). Split a module out when it needs to scale, deploy or fail on its own.

This guide calls each of those parts a **vertical**: one business capability that one team owns end to end, with
its service, its contract, its data and, when it has one, its web app. The term comes from Otto, which cut its shop
into [verticals that each belong entirely to one team](https://www.otto.de/jobs/en/blogs/techblog/on-monoliths-and-microservices_2015-09-30/).
[Self-contained systems](https://scs-architecture.org/) describe the same unit, with its own UI, logic and data, and
the micro-frontend literature calls a frontend cut this way a
[vertical split](https://docs.aws.amazon.com/prescriptive-guidance/latest/micro-frontends-aws/micro-frontend-boundaries.html).
A vertical is not Vertical Slice Architecture, which arranges the code inside one service by feature: inside a
vertical, pick an architecture style as in [Architecture](/guides/architecture/).

### Do this

1. Keep services in one repository when the same people own them and a change often touches two of them.
2. Check that each service has a reason to deploy on its own. If not, make it a module of one service instead.
3. Write the decision down as an architecture decision record (ADR), with the reason and the owning teams.

### When this is not for you

- Teams that rarely talk own the services: give each team its own repository, so ownership, access and review
  stay clear.
- One service today: start with one service in one repository. Add the monorepo structure when the second
  service is real, not before.

## 2. Where does everything go?

**In short:** one folder per vertical holding everything it owns, a flat Gradle project name for each project in it
and nothing in the root project.

```kotlin
// settings.gradle.kts: every folder in verticals/ with a service is a vertical
for (vertical in foldersWith("verticals", "service/build.gradle.kts")) {
    include(":${vertical.name}")
    project(":${vertical.name}").projectDir = vertical.resolve("service")
}
```

### What's going on

The layout answers two questions for every file: who owns it and which vertical it belongs to. When a vertical's
service, contract, web app, image, manifests and notes sit in one folder, the answers are the folder name. One line
in `CODEOWNERS` gives the folder an owner, `git log verticals/orders` is its history and moving the vertical to its
own repository later means moving one folder. Inside it, the service, the contract and the web app are siblings, so
the Java build and the Node toolchain never share a folder.

Gradle names a project after its path. Including `verticals/orders/service` as `:verticals:orders:service` makes
Gradle create empty `:verticals` and `:verticals:orders` projects for the folders above it. Gradle's best practices
recommend flat names mapped to their folders instead: `:orders` lives in `verticals/orders/service`, its contract
`:orders-api` in `verticals/orders/api`. The names stay short and every project is one you wrote.

### Do this

1. Give each vertical one folder, `verticals/<vertical>/`, with its `AGENTS.md` (step 8) and a folder per part:
   `service/` for the service's code, `Dockerfile`, `deploy/`, `compose.yaml` and `ci/smoke.sh` (steps 8 and 10),
   `api/` for its contract (step 4) and `web/` for its web app, when it has one.
2. Put deliberately reusable code in `libs/<name>/` and the shared build in `build-logic/` and `gradle/`.
3. Let `settings.gradle.kts` find the projects by their folders, each with a flat name: the `service/` folder of
   `verticals/orders` is the service `:orders`, its `api/` folder the contract `:orders-api`, a folder in `libs/` the
   library `:lib-money`. The name tells the build what a project is, and step 3 relies on it. Adding a vertical is
   adding a folder:

   ```kotlin
   fun foldersWith(dir: String, buildFile: String): List<File> =
       file(dir).listFiles { f -> f.resolve(buildFile).isFile }.orEmpty().sortedBy { it.name }

   for (vertical in foldersWith("verticals", "service/build.gradle.kts")) {
       include(":${vertical.name}")
       project(":${vertical.name}").projectDir = vertical.resolve("service")
   }

   for (vertical in foldersWith("verticals", "api/build.gradle.kts")) {
       include(":${vertical.name}-api")
       project(":${vertical.name}-api").projectDir = vertical.resolve("api")
   }
   ```

   A contract is found on its own, so a service's image build sees every contract it uses without the services
   behind them.

   Gradle's configuration cache records the folders it read, so a new folder is seen on the next build.
4. Keep no source code and no build configuration for other projects in the root project.
5. Give every folder an owner in `.github/CODEOWNERS` and turn on "Require review from Code Owners":

   ```text
   /verticals/orders/    @acme/orders
   /verticals/billing/   @acme/billing
   /build-logic/         @acme/platform
   /gradle/              @acme/platform
   ```

### When this is not for you

- A web app that serves the whole platform rather than one vertical, such as the home page and the login: give it a
  root folder of its own. A vertical's web app stays in its `web/` folder, outside the Gradle build, with its own
  toolchain (see [Next.js](/guides/nextjs/)), and generates its client from the vertical's contract file.
- Configuring the build stays slow even with the configuration cache (step 7), or several organisations share the
  repository: split it into one build per product, joined with `includeBuild`.

<a id="mono-boundaries-rule"></a>

## 3. What may services share and what must stay apart?

**In short:** services share build rules, versions, libraries and contracts. They never share domain code, a
database or each other's projects, and the build fails when one tries.

### What's going on

The fastest way to build a distributed monolith, services that can only change and release together, is to let
them read each other's insides: "common" entities, a client tied to another service's classes, a shared utility
package that grows every week. Once billing compiles against orders' classes, a change inside orders can break
billing and the two must release together.

Services that only talk through contracts (an HTTP API, a gRPC service, an event) can change their insides freely.
The contract is the only promise between them, and step 4 makes breaking it visible.

A rule in a README gets broken the first busy week. A rule in the build cannot be: the service convention plugin
(step 5) checks every project dependency when the build starts and stops at the first one that points at another
service.

<DiagramLegend items={['recommended', 'context', 'failure']} />

### Do this

1. Let a service depend only on `-api` projects and libraries. Put the check in the service convention plugin:

   ```kotlin
   // build-logic/src/main/kotlin/platform.service.gradle.kts
   // Another service is reached only through its api project (monorepo guide, step 3).
   configurations.configureEach {
       dependencies.withType<ProjectDependency>().configureEach {
           check(path == project.path || path.endsWith("-api") || path.startsWith(":lib-")) {
               "${project.path} must not depend on $path: use its api project or a library (monorepo guide, step 3)"
           }
       }
   }
   ```
2. Give the `api` and library conventions the same check with a narrower rule: they depend only on libraries. An
   `api` project that depended on its service would hand that service's code to every consumer.
3. Check the code as well as the build, in each service's `ArchitectureTest`: a class may use its own service's
   packages, the generated contracts and the libraries, nothing else of the platform. This also catches a class
   copied from another service:

   ```java
   @ArchTest
   static final ArchRule otherVerticalsOnlyThroughTheirContract = noClasses()
           .that()
           .resideInAPackage("com.acme.billing..")
           .should()
           .dependOnClassesThat(resideInAPackage("com.acme..")
                   .and(not(resideInAnyPackage("com.acme.billing..", "com.acme.api..", "com.acme.lib.."))));
   ```
4. Give each service its own database and its own migration history (see [Database](/guides/database/)).
5. Share one identity provider: every service accepts the platform's audience, so one login reaches every service
   and a call between services can pass the user's token on (see [Security hardening](/guides/security/)).
6. Create a library only for code that is deliberately reusable and owned, such as a logging setup shipped as
   Spring Boot auto-configuration. Never put shared entities or the internals of a service there. Start with no
   libraries.
7. Pick an architecture style per service and test it inside the service (see
   [Architecture](/guides/architecture/)). A layering rule that only a reviewer checks is broken within months.

### When this is not for you

- Two services that always change together and share data may really be one service. Merge them instead of
  bending the rules.

<a id="mono-contracts"></a>

## 4. Where do the contracts between services live?

**In short:** in the producing service's folder, as an `api` project that generates the code once. Consumers depend
on that project, and CI fails a breaking change.

### What's going on

A contract in a shared root folder with no owner drifts: anyone edits it, every consumer compiles its own copy of
the generated code and nobody checks that the services running in production still understand each other. When the
contract sits in the producer's folder, the producer's owners review every change to it.

The `api` project holds the contract file (OpenAPI, Protocol Buffers or an event schema) and generates the code
from it once. For OpenAPI, Spring's HTTP service interfaces serve both sides: the producer's controller implements
the interface and a consumer calls the same interface as a client. A consumer declares
`implementation(project(":orders-api"))`, so Gradle knows that a contract change affects billing, rebuilds it and
runs its tests.

The generated code goes in a package of its own, such as `com.acme.api.orders`, outside every service's packages.
The services' module checks never mistake it for a module of their own, and the rule of step 3 can allow
`com.acme.api..` for all of them.

Changing a contract in one pull request together with its consumers is the reason for one repository, but it does
not make the change safe. The old billing keeps running in production while the new orders rolls out, so a removed
field still breaks it. A breaking change takes three pull requests: add the new field and deprecate the old one,
move the consumers, then remove the old one once production no longer uses it.

### Do this

1. Keep each contract in `verticals/<vertical>/api/src/main/openapi/<vertical>.yaml` and make the folder a project
   with a `platform.api` convention plugin that generates the code into `<group>.api.<vertical>`.
2. Let consumers depend on the `api` project, never on the contract file or the producer's project.
3. In CI, compare every contract with the commit the change starts from (the pull request's base, or the previous
   commit on a push to `main`) and fail on a breaking change. Use `oasdiff` for OpenAPI and `buf breaking` for
   Protocol Buffers, against the whole `api` folder of that commit, so references between files still resolve:

   ```sh
   git fetch --depth=1 origin "$BASE_SHA"
   mkdir -p /tmp/base && git archive "$BASE_SHA" verticals/orders/api verticals/billing/api | tar -x -C /tmp/base
   oasdiff breaking /tmp/base/verticals/orders/api/openapi.yaml verticals/orders/api/openapi.yaml --fail-on ERR
   buf breaking verticals/billing/api --against /tmp/base/verticals/billing/api
   ```

   A contract that does not exist in the base yet has nothing to break: skip it.
4. Expect the last of the three pull requests, the removal, to fail the check. Approve that one on purpose once
   production no longer uses what you remove: with a label on the pull request, and with a trailer such as
   `Breaking-Change: <reason>` in the commit that lands on `main`, where the check runs again. A contract that is
   deleted counts as broken too.

### When this is not for you

- A contract that systems outside the repository consume: also publish the `api` project as a versioned artifact,
  so they do not depend on your repository layout.
- The check compares schemas; it does not run the old consumer against the new producer. Add consumer-driven
  contract tests, such as Pact, when a break reached production despite it.

## 5. How do I keep the build the same in every project?

**In short:** put the shared build in an included build called `build-logic`, as a few small convention plugins.
Every project, libraries included, applies one.

```kotlin
// settings.gradle.kts
pluginManagement { includeBuild("build-logic") }
```

### What's going on

Copying the same Java, test and quality settings into every build file works for two services. With five, the
copies drift, and the projects nobody thinks about, like a small library, silently skip the checks. The old fixes
were `buildSrc` or an `allprojects` block. Both hurt. Gradle treats `buildSrc` specially: it is built before
anything else and a change to it invalidates the configuration of every project, so Gradle's best practices prefer
an included build, which is a plugin dependency like any other. And `allprojects` pushes configuration into
projects from outside, where nobody looking at a project's build file can see it.

A convention plugin is a small recipe, such as "a Java project with our compiler checks". Each project picks the
one recipe that says what it is. The project's own build file then shows only what makes it different.

### Do this

1. Create `build-logic/` as an included build, added with `includeBuild("build-logic")` inside `pluginManagement`.
2. Start with four plugins, one per kind of project:
   - `platform.java`: toolchain, the Spring Boot versions, Error Prone, NullAway and formatting (see
     [Build quality](/guides/build-quality/)). The other three apply it.
   - `platform.library`: a plain Java library, without the Spring Boot plugin, with the boundary check of step 3.
   - `platform.api`: a library that generates code from its contract (step 4).
   - `platform.service`: the Spring Boot plugin, tests, coverage, mutation testing, the quality report, the SBOM
     and the boundary check of step 3.
3. Keep capabilities, like a database or messaging, in the service's own build file, where a reader sees what the
   service uses. A plugin per capability hides that behind names.
4. Never use `allprojects {}`, `subprojects {}` or `afterEvaluate {}`. Configure lazily and react to another plugin
   with `pluginManager.withPlugin(...)`.
5. Test the convention plugins with Gradle TestKit: apply each one to an empty project and check the tasks it
   promises, and check that a service depending on another service fails. `./gradlew build` does not run the tests
   of an included build, so CI runs `./gradlew build :build-logic:check`.

### When this is not for you

- A single service: its own build file is simpler than a plugin. Move to `build-logic` when the second service
  arrives.

## 6. How do I keep versions in one place?

**In short:** one version catalog, `gradle/libs.versions.toml`, read by every project and by `build-logic`, and no
version number anywhere else.

### What's going on

Five services with their own version numbers end up on five versions of the same library, and an upgrade becomes
five pull requests. A version catalog lists each library once under a name. Every build file uses the name, and
Renovate updates the catalog in one pull request that CI tests against every service at once. That single upgrade
is one of the best reasons to share a repository.

A catalog only helps if it is the only place. A version written straight into a build file or a convention plugin
is invisible to the catalog, and the services drift apart again.

`build-logic` is a separate build, so it does not see the catalog by itself. You import it in `build-logic`'s
settings file. Convention plugins read it through `VersionCatalogsExtension`.

A catalog states the versions you ask for. It does not force what Gradle finally resolves, so the Spring Boot bill of
materials (BOM), its list of compatible dependency versions, keeps aligning the libraries it manages (see
[Build quality](/guides/build-quality/), step 3).

### Do this

1. Keep one catalog at `gradle/libs.versions.toml` with every library and plugin, and write no version anywhere
   else.
2. Import it in `build-logic`'s settings, with the repositories its plugins come from:

   ```kotlin
   // build-logic/settings.gradle.kts
   dependencyResolutionManagement {
       repositories {
           mavenCentral()
           gradlePluginPortal()
       }
       versionCatalogs {
           create("libs") { from(files("../gradle/libs.versions.toml")) }
       }
   }
   ```
3. Apply `kotlin-dsl` in `build-logic` and declare the external Gradle plugins your conventions use as its
   dependencies. A plugin from the catalog becomes a dependency through its marker artifact:

   ```kotlin
   // build-logic/build.gradle.kts
   plugins { `kotlin-dsl` }

   fun plugin(p: Provider<PluginDependency>) = p.map { "${it.pluginId}:${it.pluginId}.gradle.plugin:${it.version}" }

   dependencies {
       implementation(plugin(libs.plugins.spring.boot))
   }
   ```
4. Import the Spring Boot BOM as a `platform` in `platform.java`, so libraries and `api` projects get the same versions
   as the services that use them.
5. When you must override a version the BOM manages, add a constraint with a reason.

### When this is not for you

- A service that truly needs a different version of a library: give that version its own name in the catalog with
  the reason in a comment, and plan the upgrade that brings it back in line.

## 7. How does the build stay fast as it grows?

**In short:** let Gradle skip the work it has already done: turn on the configuration cache, the build cache and
parallel execution, and share the build cache from `main` with every pull request.

```properties
# gradle.properties
org.gradle.configuration-cache=true
org.gradle.caching=true
org.gradle.parallel=true
```

### What's going on

Gradle already builds only what changed, as long as it remembers what it did. The build cache stores the output of
each cacheable task, such as compiling or testing, under a key made from all of its declared inputs. When billing
changes, orders' compile and test tasks have the same inputs as before and come back from the cache in
milliseconds. The configuration cache does the same for the setup phase, which otherwise runs every build script
on every run.

So the cheapest answer to "which services do we rebuild?" is: all of them, with a warm cache. Gradle works out what
changed from the declared inputs. A list of paths someone wrote by hand goes stale.

This goes one step further than the pipeline of a single service, which caches downloads and reruns every test
(see [CI pipelines](/guides/ci-pipelines/), step 4). With many services, rerunning the tests of the ones nobody
touched is most of the build. Reusing a test result is safe only when everything the test depends on is an input
Gradle sees: a container image pinned by digest is, a shared test database or a moving image tag is not.

A cache is only as trustworthy as whoever writes to it. Builds of `main` save it; pull requests restore it and do
not save, since their results would only serve that pull request.

### Do this

1. Commit the three lines above in `gradle.properties`.
2. In CI, restore Gradle's build cache from the mounted `GRADLE_USER_HOME` on every run and save it only on pushes
   to `main`:

   ```yaml
   - uses: actions/cache/restore@55cc8345863c7cc4c66a329aec7e433d2d1c52a9 # v6.1.0
     with:
       path: ~/.cache/gradle-ci/caches/build-cache-1
       key: gradle-build-cache-${{ github.sha }}
       restore-keys: gradle-build-cache-
   # ... the Gradle build in the pinned JDK image ...
   - if: github.event_name == 'push' && github.ref == 'refs/heads/main'
     uses: actions/cache/save@55cc8345863c7cc4c66a329aec7e433d2d1c52a9 # v6.1.0
     with:
       path: ~/.cache/gradle-ci/caches/build-cache-1
       key: gradle-build-cache-${{ github.sha }}
   ```
3. Declare the inputs and outputs of every task you write in `build-logic`, and pin every container image a test
   starts by digest. A test with an input Gradle cannot see can come back from the cache with a stale result.
4. Write build logic that does not reach into other projects, as step 5 asks. It is what the configuration cache
   needs today and what Gradle's Isolated Projects, still incubating, will require.
5. Measure before you optimise further: run the same command twice with `--scan` or `--profile` and look at what
   still runs.

### When this is not for you

- A remote build cache shared with laptops: worth it for large teams, but only CI may write to it, and it is one
  more service to run.

## 8. How do I work on just one service?

**In short:** address the service by its project name. Its own `compose.yaml` starts only what it needs, and its
own `AGENTS.md` tells a coding agent its rules.

```sh
./gradlew :orders:build
./gradlew :orders:bootRun
```

### What's going on

Gradle builds a task and whatever it depends on, nothing more. If billing does not depend on orders, building
orders never touches billing. That holds because of the boundaries from step 3.

Running a service locally is the same idea. Spring Boot's Docker Compose support starts the `compose.yaml` it finds
in the working directory, and `bootRun` runs in the service's folder, so each service starts only its own
database and broker (see [Local development](/guides/local-development/)). A root `compose.yaml` includes every
service's file to start the dependencies of all of them at once. The included files share one set of names, so
each service prefixes what it defines.

Coding agents work the same way. They read the `AGENTS.md` nearest to the file they edit, so a short one in each
service gives its style, its commands and its owner, while the root one keeps the map and the rules of steps 2 to 6.

### Do this

1. Give every service the same commands: `./gradlew :<service>:build`, `:<service>:test` and `:<service>:bootRun`.
2. Put what every service needs on the laptop, such as Grafana LGTM and a mock identity provider, in one
   `platform.compose.yaml` that each service's `compose.yaml` includes. Give every Compose file the platform's
   project `name`, so services started one by one share those containers instead of fighting over their ports, and
   set `spring.docker.compose.lifecycle-management` to `start-only`, so one service stopping leaves them running. Put
   each service's own dependencies in its `verticals/<vertical>/service/compose.yaml` and prefix every Compose
   service, volume and network with the vertical's name, such as `orders-postgres`.
3. Give each service its own local ports in `bootRun`, such as 8110 and 8111 for management, so several run side by
   side.
4. Add a root `compose.yaml` that includes them all (Docker Compose 2.20.3 or later) and check the combined result
   with `docker compose config`:

   ```yaml
   include:
     - verticals/orders/service/compose.yaml
     - verticals/billing/service/compose.yaml
   ```
5. Write a root `AGENTS.md` with the layout and the rules, and an `AGENTS.md` in each service with its
   architecture style, its commands and what it must never depend on.

### When this is not for you

- A change in `build-logic`, the catalog, a contract or a library affects every project that uses it. Build them
  all for that change: `./gradlew build`.

<a id="mono-ci"></a>

## 9. How should CI decide what to build?

**In short:** one workflow that always runs, builds and tests every project in one Gradle run and ends in a single
gate job. Make that gate the only required check.

### What's going on

The obvious idea is one workflow per service with a path filter. It breaks in two ways. A workflow skipped by its
path filter leaves its required check pending, so a pull request that touches only the catalog, or a Renovate
update, can never merge. And the path lists are copied by hand into every workflow, so they go stale the day a
service gains a dependency.

One workflow that always runs avoids both. It builds everything, which step 7 makes cheap: Gradle, not a path list,
decides what really runs. A gate job at the end checks that every job it needs passed. The gate always reports, so
it can be the one required check, and every other job, the frontend's included, feeds it.

### Do this

1. Run one workflow on `pull_request`, on pushes to `main` and on `merge_group` if you use a merge queue.
2. Build and test every project in one job with `./gradlew build :build-logic:check`, in the pinned JDK (see
   [CI pipelines](/guides/ci-pipelines/), step 3), and run the contract checks of step 4 in the same job. Gradle
   runs the projects in parallel and the cache skips what did not change.
3. Call one reusable workflow per vertical for its manifests, image, scan and smoke test (step 10), through a
   matrix built from the folders in `verticals/`, so a new vertical is picked up without editing the workflow.
4. End with a gate job that runs with `if: always()`, needs every other job and fails unless all of them passed.
   Make it the only required check:

   ```yaml
   jobs:
     build:
       # ./gradlew build :build-logic:check and the contract checks
     vertical:
       needs: [build]
       strategy:
         matrix:
           vertical: ${{ fromJSON(needs.build.outputs.verticals) }}
       uses: ./.github/workflows/vertical.yml
       with:
         vertical: ${{ matrix.vertical }}
     gate:
       if: always()
       needs: [build, vertical]
       runs-on: ubuntu-24.04
       steps:
         - env:
             RESULTS: ${{ join(needs.*.result, ' ') }}
           run: for r in $RESULTS; do test "$r" = success; done
   ```

### When this is not for you

- A build that takes too long even with a warm cache: split the tests that need containers into their own jobs
  first. Tools that pick tests by change, such as Develocity's Predictive Test Selection, come after that.

## 10. How does each service ship on its own?

**In short:** one image, one deployment folder and one history per service, and the same digest moves from one
environment to the next.

### What's going on

Sharing a repository must not mean sharing a release. If orders can only ship when billing is ready, the
repository has become a release train where the slowest service sets the pace for all.

Each service gets its own image and its own manifests, and its deployment changes only when its image does. A
service image is built from the repository root, because the service folder alone cannot see `build-logic`, the
contracts or the libraries. In CI it receives the jar the build job already tested, so what ships is what passed.

Building every image on every change is simple and always right, and Gradle has already skipped the compile and
test work. Skipping an image too is tempting, but only safe when you can prove it would come out the same. Gradle 9
makes archives reproducible, yet two clean builds of the same commit of the generated platform give different Boot
jars: the SBOM inside carries a new serial number and timestamp each time. An image also depends on its
`Dockerfile`, the files it copies and its base image.

### Do this

1. Give each service its own image repository, such as `ghcr.io/acme/orders`.
2. Build each image from the repository root with the service's `Dockerfile`, and pass it the tested jar through a
   named build context (`--build-context`). Give each `Dockerfile` an allow list next to it,
   `Dockerfile.dockerignore`: the shared build, the libraries, every contract and that service, so a change inside
   another service never reaches its context.
3. Let each service own its smoke test, `verticals/<vertical>/service/ci/smoke.sh`, which the reusable workflow
   runs against the new image.
4. Tag images with the commit, promote the same digest from one environment to the next and record the commit in
   its provenance (see [CI pipelines](/guides/ci-pipelines/), step 6).
5. Keep each service's Kubernetes manifests in its own `deploy/` folder (see
   [Kubernetes manifests](/guides/kubernetes-manifests/)). Updating one service's image never touches another's.
6. Build and smoke-test every service's image on every change until the image builds are the slow part. Then skip
   a service only when a hash of everything its image is made from, stored as a label on the image of `main`, is
   unchanged, and only after two clean builds of the same commit gave the same jar.

### When this is not for you

- Libraries and `api` projects: they are project dependencies, not releases. Publish one, with a version, only
  when something outside the repository uses it.
