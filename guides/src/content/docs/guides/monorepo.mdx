Your team owns five services, so you put them in one repository. A year later, a change in billing breaks the
orders build, every pull request runs every test and nobody can release orders without a billing fix going out
with it. You built one big service with five deployments.

This guide shows how to keep the good parts of one repository (one build, one place for contracts, one CI) while
each service stays separate: its own code, database, image and release.

<GuideStatus guide="monorepo" />

<a id="mono-when"></a>

## 1. Should our services share one repository?

**In short:** yes, when one team owns the services and changes them together often. Keep them apart when
different teams own them or they release on unrelated schedules.

### What's going on

A shared repository is like a shared office. Working side by side makes small cross changes easy: rename a field
in a contract and fix its consumer in one pull request. But a shared office only works if everyone keeps their
own desk. When services start reading each other's code, the office turns into one big room where nobody can move
anything alone.

The repository is not the problem. Coupling is. One repository makes coupling easy to add and hard to see, so it
needs rules that a separate repository gets for free.

### Do this

1. Put services in one repository when the same team owns them and a change often touches two of them.
2. Decide the boundaries before the second service arrives (steps 2 and 3).
3. Write the decision down as an architecture decision record, with the reason.

### When this is not for you

- Different teams own the services: give each its own repository, so ownership and access stay clear.
- One service: start with one service in one repository. Add the monorepo structure when the second service is
  real, not before.

<a id="mono-boundaries-rule"></a>

## 2. What may services share and what must stay apart?

**In short:** services share build rules, versions and contracts. They never share domain code, a database or
each other's projects.

### What's going on

The fastest way to build a distributed monolith is a shared module: "common" entities, a shared client, a shared
utility package that grows every week. Once billing compiles against orders' classes, a change in orders can break
billing and the two must release together.

Services that only talk through contracts (an HTTP API, a gRPC service, an event) can change their insides freely.
The contract is the only promise between them.

### Do this

1. Never add a project dependency from one service to another.
2. Give each service its own database and its own migration history.
3. Create a library under `libs/` only for code that is deliberately reusable, never for shared entities or the
   internals of a service. Start with no libraries.
4. Pick an architecture style per service; inside one service, every capability uses the same style.

### When this is not for you

- Two services that always change together and share data may really be one service. Merge them instead of
  bending the rules.

<a id="mono-contracts"></a>

## 3. Where do the contracts between services live?

**In short:** next to the code, in `contracts/<service>/`, owned by the service that produces them and checked in
CI.

### What's going on

A contract in a shared root folder with no owner drifts: anyone edits it, nobody checks that old consumers still
work. When the producing service owns its contract, a breaking change shows up in that service's pull request,
where the right people review it.

Consumers should not read the contract file straight from a sibling folder. They depend on a client project
generated from it, so the build knows that a contract change affects them.

### Do this

1. Keep each contract in `contracts/<service>/`, split by kind (`openapi`, `proto`, `avro`).
2. Make the producing service the owner, for example with a CODEOWNERS entry.
3. In CI, compare the contract with its last released version and fail on a breaking change.
4. Generate a client project from the contract. Consumers depend on that project, never on the folder.

### When this is not for you

- A contract shared with systems outside the repository: publish it as a versioned artifact as well, so outside
  consumers do not depend on your repository layout.

<a id="mono-build-logic"></a>

## 4. How do I keep the build the same in every service?

**In short:** put shared build rules in an included build called `build-logic`, as small convention plugins that
each service applies.

```kotlin
// settings.gradle.kts
pluginManagement { includeBuild("build-logic") }
```

### What's going on

Copying the same Java, test and quality settings into every build file works for two services. With five, the
copies drift. The old fixes were `buildSrc` or an `allprojects` block. Both hurt: Gradle's own guidance prefers an
included build, because any change in `buildSrc` makes the whole build out of date. An `allprojects` block applies
its configuration everywhere, even where it does not belong.

A convention plugin is a small recipe, such as "a Java project with our compiler checks". Each service picks the
recipes it needs in its `plugins {}` block and nothing else.

### Do this

1. Create `build-logic/` as an included build, added with `includeBuild("build-logic")` inside `pluginManagement`.
2. Start with few plugins: one for Java (toolchain, compiler checks, formatting), one for tests, one for a Spring
   Boot service. Add more only when you see real duplication.
3. Keep capabilities, like a database or messaging, in the service's own build file, not in a convention.
4. Never use `allprojects {}` or `subprojects {}`.
5. Test the convention plugins themselves with Gradle TestKit.

### When this is not for you

- A single service: its own build file is simpler than a plugin. Move to `build-logic` when the second service
  arrives.

<a id="mono-catalog"></a>

## 5. How do I keep versions in one place?

**In short:** one version catalog, `gradle/libs.versions.toml`, read by every service and by `build-logic`.

### What's going on

Five services with their own version numbers end up on five versions of the same library and upgrades become five
pull requests. A version catalog lists each library once under a name. Every build uses that name.

`build-logic` is a separate build, so it does not see the catalog by itself. You import it in `build-logic`'s
settings file. Convention plugins read it through `VersionCatalogsExtension`.

A catalog states the versions you ask for. It does not force what Gradle finally resolves, so the Spring Boot BOM
keeps aligning the libraries it manages.

### Do this

1. Keep one catalog at `gradle/libs.versions.toml` and add every library there.
2. In `build-logic/settings.gradle.kts`, import it with
   `versionCatalogs { create("libs") { from(files("../gradle/libs.versions.toml")) } }`.
3. Declare the external Gradle plugins your conventions use as dependencies of `build-logic`.
4. Keep the Spring Boot BOM for the libraries it manages. When you must override one, add a constraint with a
   reason.

### When this is not for you

- A service that truly needs a different version of a library: that is a sign it should live in its own
  repository or that the upgrade should happen everywhere.

<a id="mono-one-service"></a>

## 6. How do I build and run just one service?

**In short:** give each service a short project name mapped to its folder, then run tasks by that name.

```sh
./gradlew :orders:build
```

### What's going on

Gradle builds a task and whatever it depends on, nothing more. If billing does not depend on orders, building
orders never touches billing. That only holds while the boundaries from step 2 hold.

Including a nested service as `:services:orders` makes Gradle create an empty `:services` project for the folder
above it. A flat name mapped to the folder avoids those empty projects and keeps task names short.

### Do this

1. In `settings.gradle.kts`, include each service by a flat name and set its folder:
   `include("orders")` and `project(":orders").projectDir = file("services/orders")`.
2. Keep no source code in the root project.
3. Build or test one service with `./gradlew :orders:build`.
4. Give every service the same commands (build, test, run, lint), so moving between services needs no new habits.

### When this is not for you

- A change in `build-logic`, the catalog, a contract or a library affects every service that uses it. Build them
  all for that change.

<a id="mono-ci"></a>

## 7. How should CI decide what to build?

**In short:** one workflow that always runs, starts a job per service and ends in a single gate job. Make that
gate the only required check.

### What's going on

The obvious idea is one workflow per service with a path filter. It breaks branch protection: when a workflow is
skipped by a path filter, its required check stays pending and the pull request can never merge.

A workflow that always runs avoids that. It decides which services to build, calls a reusable workflow for each
one and finishes with a gate job that checks every expected job passed. The gate always reports, so it can be the
one required check.

### Do this

1. Write one reusable workflow that builds, tests and packages a single service.
2. Write one orchestration workflow that runs on every pull request and calls it for each service, through a
   matrix.
3. End with a gate job that runs with `if: always()` and fails when any expected job failed or was skipped.
4. Start by building every service on every change. Build only the affected services later, once you can compute
   which services depend on a changed contract, library, catalog or convention. When unsure, build everything.

### When this is not for you

- No branch protection with required checks: path filters work but you lose the safety that a skipped build
  cannot be merged by mistake.

<a id="mono-ship"></a>

## 8. How does each service ship on its own?

**In short:** one image, one deployment folder and one release history per service.

### What's going on

Sharing a repository must not mean sharing a release. If orders can only ship when billing is ready, the
repository has become a release train where the slowest service sets the pace for all.

Each service gets its own image and its own manifests. You promote the exact image you tested. A service
image is built from the repository root, because the service folder alone cannot see `build-logic`, the
contracts or the libraries.

### Do this

1. Give each service its own image repository.
2. Build each image from the repository root with a service target, for example a build argument that names the
   service.
3. Promote the same image digest from one environment to the next. Record the source commit in its provenance.
4. Keep each service's Kubernetes manifests in its own `deploy/` folder (see
   [Kubernetes manifests](/guides/kubernetes-manifests/)).
5. Version and tag releases per service, so the history of one service is readable on its own.

### When this is not for you

- Libraries inside the repository: they are project dependencies, not releases. Publish a library only when
  something outside the repository uses it.

## Put it all together

Everything above lands in the repository layout, the settings file and one CI workflow.

### The layout

- `settings.gradle.kts`: `pluginManagement { includeBuild("build-logic") }` and a flat name for each service
  (step 6).
- `build-logic/`: a few convention plugins, with their own tests (step 4).
- `gradle/libs.versions.toml`: the only version catalog (step 5).
- `contracts/<service>/`: each contract with its owner, plus a generated client project (step 3).
- `services/<service>/`: code, build file, Dockerfile and `deploy/` of one service (steps 2 and 8).
- `libs/`: empty until code is deliberately reusable (step 2).
- `docs/adr/`: the decision to share a repository and every exception to the rules (steps 1 and 2).

### In CI

- One orchestration workflow on every pull request, a reusable workflow per service and a gate job as the only
  required check (step 7).
- A compatibility check for every contract against its last release (step 3).
- One image per service, built from the root and promoted by digest (step 8).
