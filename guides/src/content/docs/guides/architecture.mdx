A new developer opens the service and asks where the order rules live. Someone answers "in OrderService, a bit in
the controller and the SQL handles the rest". Every change touches five packages and nobody is sure what
breaks. The code works; its shape does not tell you anything.

This guide gives a service a shape you can explain in one sentence and check in a test: split by business
capability first, then pick one style inside each capability. It is how the services generated by the Initializer
are organised. For a wider look at other styles, read [Architecture styles compared](/guides/architecture-styles/).

## 1. How should I split the service into parts?

**In short:** by business capability first. Each capability is one package under the base package and one Spring
Modulith module.

```text
io.acme.orders/
  ordering/      a capability: one Modulith module
  billing/       another capability
```

### What's going on

Most services start split by technical role: all controllers in one package, all services in another, all
repositories in a third. That looks tidy until you change one feature and touch every package.

Think of a hospital. You do not put every doctor in one room and every bed in another. You build departments,
and each department has its own doctors and beds. A capability is a department: ordering, billing, shipping. It
owns its rules and its data. Other capabilities talk to it through a small front desk.

Spring Modulith turns that into something a test can check. Each package right under the main package is a
module. Its nested packages are internal: other modules may only use the types in the module's base package or
packages it exposes on purpose.

### Do this

1. Create one package per capability right under the base package of the application class.
2. Give each capability a small API at its root: a facade or a few narrowly named interfaces. Keep everything
   else in nested packages, which Modulith treats as internal.
3. Start without a shared module. If you need one later, keep it closed, export as little as possible and let it
   depend on no capability.
4. Run `ApplicationModules.of(Application.class).verify()` in a test (step 7).

### When this is not for you

- A tiny service with a single capability: you still get the package. The module boundaries only start to
  pay off with the second capability.
- A capability is a business boundary, not one database table. If you end up with one module per entity, merge
  them.

<a id="arch-style-choice"></a>

## 2. What goes inside each capability?

**In short:** pick one style and use it in every capability of the service: hexagonal or DDD layered.

### What's going on

The split by capability decides which parts exist. The style decides how the code inside one part is arranged and
which way its dependencies point. They are separate decisions, so you can change one without the other.

Both styles keep the business rules in a `domain` package that knows nothing about the web or the database. They
differ in how they name and wire the rest.

| Style | Inside `<capability>/` |
| ----- | ---------------------- |
| Hexagonal | `domain/`, `application/port/in/`, `application/port/out/`, `application/service/`, `adapter/in/`, `adapter/out/` |
| DDD layered | `presentation/`, `application/`, `domain/`, `infrastructure/` |

### Do this

1. Choose the style once per service and write it down.
2. Use the same package names in every capability, so a developer who knows one knows them all.
3. Give every handwritten class a role in that layout. A class without a place is a class no rule checks.

### When this is not for you

- You need a different style in one service of a monorepo: that is allowed, one style per service, with the
  reason written in an ADR.
- Simple create, read, update and delete over a table: the classic controller, service and repository shape may
  be enough. See [when classic layered is enough](/guides/architecture-styles/#style-layered).

<a id="arch-hexagonal"></a>

## 3. How does hexagonal work?

**In short:** the application talks to the outside world only through ports. Adapters plug the world into
those ports.

### What's going on

Alistair Cockburn described the idea as letting an application "equally be driven by users, programs, automated
test or batch scripts" and be "developed and tested in isolation from its eventual run-time devices and
databases".

Picture a games console. The console defines the shape of the controller port and the shape of the display port.
Any controller that fits the port works and the console does not care who made it. In code:

- An **inbound port** (`application/port/in`) is what the capability offers, such as `PlaceOrder`.
- An **application service** (`application/service`) implements it and holds the use case.
- An **outbound port** (`application/port/out`) is what the use case needs, such as `Orders` to load and save.
- **Adapters** (`adapter/in`, `adapter/out`) connect the real world: a REST controller calls an inbound port; a
  JDBC repository implements an outbound port.

### Do this

1. Put the use case behind an inbound port and implement it in an application service.
2. Let the application service reach the database and other systems only through outbound ports.
3. Use domain types in port signatures, never web or persistence types.
4. Mark the packages with jMolecules: `@PrimaryPort`, `@SecondaryPort`, `@PrimaryAdapter`, `@SecondaryAdapter`
   and `@Application`.

### When this is not for you

- One capability with one entry point and no outbound system: the ports add files without adding freedom.
- Your team thinks in DDD layers already: step 4 gives the same protection with names they know.

<a id="arch-ddd-layered"></a>

## 4. How does DDD layered work?

**In short:** four layers, presentation, application, domain and infrastructure, with the domain at the bottom of
every arrow.

### What's going on

Eric Evans' layered architecture splits a program into layers that each depend "only on the layers below", with
the domain model isolated from the user interface, application and infrastructure code. In the classic picture
infrastructure sits at the very bottom, so the domain may call it. That is exactly the dependency a modern service
does not want: business rules that import a database client.

The Initializer uses a dependency inverted variant. Infrastructure still holds the database code but it points
up at the domain instead of the other way round:

| Layer | May depend on |
| ----- | ------------- |
| `presentation` | `application` and `domain` |
| `application` | `domain` |
| `infrastructure` | `application` and `domain` |
| `domain` | nothing outside itself |

Only the composition root, the `config` package, sees every layer, because it wires them together.

### Do this

1. Put controllers in `presentation`, use cases in `application`, rules in `domain` and database or client code
   in `infrastructure`.
2. Define repository interfaces in `domain` or `application`; implement them in `infrastructure`.
3. Write the dependency graph above as your own ArchUnit rule. jMolecules' `ensureLayering()` allows every layer
   to use the layers below it, including domain to infrastructure, so it does not enforce this variant.

### When this is not for you

- You want the library to enforce the rules for you with one line: hexagonal with `ensureHexagonal(STRICT)` gives
  you that (step 7).
- Notice the overlap: this variant and hexagonal produce almost the same dependency graph. Pick the vocabulary
  your team will use correctly.

<a id="arch-transactions"></a>

## 5. Where does the transaction start?

**In short:** in the application service, one transaction per use case.

```java
@Transactional
public OrderId place(PlaceOrderCommand command) { ... }
```

### What's going on

A use case such as "place an order" must load data, check a rule and save the result as one unit: all of it
happens or none of it does. The question is which class says where that unit begins.

If the controller opens it, web code decides about database work. If the repository opens it, every save is its
own unit and a rule that spans two saves can break halfway. If the domain opens it, the rules depend on Spring.
The application service is the one place that knows the whole use case, so it owns the boundary.

### Do this

1. Put `@Transactional` on the public methods of application services, one method per use case.
2. Keep adapters and the domain free of transaction annotations.
3. Let other capabilities react after commit through events instead of joining your transaction.

### When this is not for you

- A read that touches one table and no rule: a read only transaction or none is fine.
- Work that must survive a failure in the next step, such as sending a message: that needs an outbox, which the
  messaging guides cover.

<a id="arch-pure-domain"></a>

## 6. How do I keep the domain free of Spring?

**In short:** let the domain depend only on the JDK, JSpecify and itself. Fail the build if anything else
leaks in.

### What's going on

The domain is the part you want to keep for years. Frameworks change every few years; your pricing rules should
not have to. If a domain class imports a Spring annotation or a database type, every framework upgrade becomes a
domain change and the rules can no longer be tested without starting a container.

A domain class should be plain Java: records, enums, classes with methods that enforce rules. Persistence mapping
lives in the adapters or infrastructure, which translate between database rows and domain objects.

### Do this

1. Write the domain in plain Java. Records work well for values.
2. Map between domain objects and database rows in the outbound adapter or the infrastructure layer.
3. Add an ArchUnit rule that the `domain` package only depends on `java..`, `org.jspecify..` and itself. The
   fixture's rule is in the last section.

### When this is not for you

- You use jMolecules DDD annotations such as `@AggregateRoot` in the domain: allow `org.jmolecules..` in the rule.
  They are annotations without behaviour.

<a id="arch-rules-tested"></a>

## 7. How do tests keep the rules true?

**In short:** three checks run with every build: Modulith's `verify()`, jMolecules' `ensureHexagonal(STRICT)` and
two rules of your own.

### What's going on

An architecture that lives only in a wiki is gone after a few months of deadlines. A test that fails the build
when a class reaches across a boundary keeps it.

- `ApplicationModules.of(Application.class).verify()` fails on cycles between modules and on any use of another
  module's internal types.
- `JMoleculesArchitectureRules.ensureHexagonal(VerificationDepth.STRICT)` checks who may call whom among the
  annotated ports, adapters and application code. In `STRICT` no adapter or port may touch `@Application` code
  directly.
- Two rules close the gaps the library leaves: the domain depends on nothing else and nothing outside the
  adapters depends on them.

There is a trap. In `STRICT`, a port may only reference ports and classes without a hexagonal annotation. If you
mark the domain as `@Application`, every port signature that uses a domain type breaks the rule. So the domain
stays unannotated. Unannotated classes are not checked by the library at all. That is why the domain needs its
own rule.

### Do this

1. Add a `ModulithTest` that calls `verify()`.
2. Add an `ArchitectureTest` with `ensureHexagonal(VerificationDepth.STRICT)`.
3. Leave the `domain` package without a jMolecules hexagonal annotation and constrain it with your own rule.
4. Add a rule that nothing outside `..adapter..` depends on `..adapter..`.

### When this is not for you

- DDD layered: replace the jMolecules rule with your own layered graph from step 4.
- Exclusions are sometimes needed, for generated code for example. Keep each one narrow and named.

<a id="arch-limits"></a>

## 8. What can the tests not prove?

**In short:** that your boundaries are good. They prove the code follows the boundaries you drew, not that you
drew them in the right place.

### What's going on

Architecture tests check arrows between packages. They cannot tell whether "ordering" and "billing" are the right
split, whether a class in `domain` holds real business rules or just getters and whether a module could be
deployed on its own one day. A service can pass every check and still be a tangle, with all the logic in one
module named `core`.

### Do this

1. Review the module list when a new capability appears: does it match how the business talks?
2. Watch for modules that change together in almost every pull request. They may be one capability.
3. Treat green architecture tests as a floor, not as proof of good design.

### When this is not for you

- It always applies. No tool replaces talking to the people who know the business.

### In every new capability

- One package under the base package, with a small API at its root (step 1).
- The same style and package names as the other capabilities (step 2).
- `@Transactional` on application service methods only (step 5).
- A plain Java domain, mapped by adapters (step 6).
