The database fails over at 3 a.m. Thirty seconds later every pod of your service restarts at once and each one
hits the database while it is still recovering. Next day a routine deploy returns a burst of 502s. Nothing in the
code changed: the Deployment and the app disagree about how pods start, stop and fail.

This guide sets the eight Deployment decisions that make them agree: probes, shutdown, resources, rollouts,
disruptions, scaling, placement and scheduled work. How the manifests are packaged is in
[Kubernetes manifests](/guides/kubernetes-manifests/) and JVM sizing is in
[The JVM in containers](/guides/jvm-in-containers/).

<a id="kube-probes"></a>

## 1. What should each probe check?

**In short:** liveness asks "is this process broken?", readiness asks "should this pod get traffic now?". Neither
checks the database.

```yaml
management.endpoint.health.probes.add-additional-paths: true
```

### What's going on

Kubernetes asks your pod three questions and does something different with each answer:

| Probe | Question | On failure |
| ----- | -------- | ---------- |
| `startupProbe` | Has the process finished starting? | Waits up to its budget, then restarts the container |
| `livenessProbe` | Is the process broken in a way only a restart fixes? | Restarts the container |
| `readinessProbe` | Should this pod receive new requests right now? | Takes the pod out of the Service, no restart |

Spring Boot answers from its own lifecycle, not from health checks. Liveness is `CORRECT` once the context has
started. Readiness turns to "accepting traffic" when startup finishes and back to "refusing" the moment shutdown
begins.

Now picture the database in liveness. The database fails over and every pod fails the check. Kubernetes restarts
all of them together. A database in readiness is gentler but still takes every pod out of rotation at once, so the
gateway returns 503 even for routes that never touch the database.

### Do this

1. Set `add-additional-paths: true`, so `/livez` and `/readyz` are served on the main port 8080. A probe on the
   management port would still pass while the main connector is stuck.
2. Point liveness at `/livez` and readiness at `/readyz`. Leave both groups at their defaults.
3. Use a `startupProbe` instead of `initialDelaySeconds`, sized from measured startup, as in
   [step 8 of the JVM guide](/guides/jvm-in-containers/#jvm-startup-probe).
4. Set `timeoutSeconds: 2` on every probe. The default of 1 second can fail during a long GC pause.
5. If Spring Security is on, let `/livez` and `/readyz` through without authentication.

### When this is not for you

- A dependency that can fail for one pod only, such as a cache local to the node: add it to readiness with
  `group.readiness.include: readinessState,<name>`. Keep `readinessState` in the list or the pod never leaves
  rotation at shutdown.
- The main port uses mutual TLS that the kubelet cannot present: probe the management port instead.

<a id="kube-graceful-shutdown"></a>

## 2. How do I stop a pod without failing requests?

**In short:** give the routers 10 seconds to forget the pod before it stops and fit the whole shutdown inside the
grace period.

```yaml
spring.lifecycle.timeout-per-shutdown-phase: 20s
```

### What's going on

When a pod is deleted, two things start at the same time and nothing orders them. The routers (kube-proxy, the
gateway, a load balancer) learn that the pod is going away, which takes from under a second to several seconds.
Meanwhile the kubelet tells the app to stop.

It is like closing a shop while the sign outside still says "open": if you lock the door right away, the customers
already walking over find it shut. A short wait before locking fixes that.

Spring Boot's defaults do not fit Kubernetes' defaults: Boot allows 30 seconds per shutdown phase while Kubernetes
kills the pod after 30 seconds in total.

### Do this

1. Add a `preStop` hook with the native `sleep` action of 10 seconds. It needs no shell, so it works in distroless
   images.
2. Set `spring.lifecycle.timeout-per-shutdown-phase: 20s`. Graceful shutdown itself is already the default.
3. Set `terminationGracePeriodSeconds: 45`. It counts from deletion and includes the `preStop` time.
4. Make sure the JVM is PID 1 with an exec form `ENTRYPOINT`. `sh -c "java ..."` swallows the signal.

### When this is not for you

- Long requests such as uploads or streaming: raise the phase timeout and the grace period together.
- An external load balancer that updates slowly: measure how long it takes and lengthen the `preStop` sleep.
- Clusters older than Kubernetes 1.34: use `exec` with `sleep 10` instead, which needs a shell in the image.

<a id="kube-resources"></a>

## 3. How much CPU and memory should the pod ask for?

**In short:** memory request equal to the limit; a CPU request and no CPU limit.

```yaml
resources:
  requests: { cpu: "1", memory: 1Gi }
  limits:   { memory: 1Gi }
```

### What's going on

Memory cannot be shared or slowed down. If the request is below the limit, the node is promised more memory than
it has. When it runs short, something gets killed.

CPU can be shared and a limit hurts the JVM more than it helps. Kubernetes enforces it as a quota every 100
milliseconds. The JVM runs many threads at once, so it can spend a 1 CPU quota in the first 25 milliseconds and then
wait 75. That shows up as latency spikes and longer GC pauses while the CPU graph looks calm.

The request is what the scheduler reserves for you and under contention it guarantees your share.

### Do this

1. Set the memory request equal to the limit and size the heap from it as in
   [step 1 of the JVM guide](/guides/jvm-in-containers/#jvm-heap-sizing).
2. Set an honest CPU request. The autoscaler measures CPU as a percentage of it.
3. Leave out the CPU limit and set `-XX:ActiveProcessorCount`, as in
   [step 3 of the JVM guide](/guides/jvm-in-containers/#jvm-cpu-count).

### When this is not for you

- A namespace quota requires CPU limits: set the limit to about twice the request and drop `ActiveProcessorCount`.
  Watch the throttling ratio.
- Without a CPU limit the pod is `Burstable`, not `Guaranteed`. With memory request equal to the limit, it still
  never uses more memory than it asked for.

<a id="kube-rollout"></a>

## 4. How do I roll out a new version without losing capacity?

**In short:** add one new pod, wait until it is ready, remove one old pod, repeat.

```yaml
strategy:
  rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
minReadySeconds: 10
```

### What's going on

The default rolling update may take pods away before their replacements serve. With `maxUnavailable: 0` the
service never drops below the number of pods you run. `minReadySeconds` makes Kubernetes wait a little after
a pod turns ready, so a pod that crashes right after starting stops the rollout.

The cost is time: one step per pod and room in the cluster for one extra pod.

### Do this

1. Set `maxSurge: 1` and `maxUnavailable: 0`.
2. Set `minReadySeconds: 10`.
3. Leave `spec.replicas` out of the Deployment when an autoscaler owns the count. Otherwise every deploy resets it.

### When this is not for you

- Deployments with 20 or more replicas: use `maxSurge: 25%` or a rollout takes an hour.

<a id="kube-disruption"></a>

## 5. How do I survive node drains and cluster upgrades?

**In short:** a PodDisruptionBudget that lets one pod go at a time and never blocks a drain.

```yaml
spec:
  maxUnavailable: 1
  unhealthyPodEvictionPolicy: AlwaysAllow
```

### What's going on

Node upgrades and the cluster autoscaler drain nodes, evicting the pods on them. A PodDisruptionBudget says how
many of your pods may be evicted at once. It covers only these planned evictions, not a node that crashes.

Two settings go wrong often. `minAvailable: 3` on a service with 3 replicas blocks every drain, so cluster
upgrades hang. And a pod stuck crashing can block a drain too, unless the budget allows evicting pods that are
running but not ready.

### Do this

1. Create a PodDisruptionBudget with `maxUnavailable: 1`. It works at any replica count.
2. Set `unhealthyPodEvictionPolicy: AlwaysAllow`, so a broken pod cannot hold a node upgrade hostage.
3. Run at least 3 replicas in production.

### When this is not for you

- It always applies to services. A single replica job has nothing to protect: skip the budget there.

<a id="kube-autoscaling"></a>

## 6. How should the service scale?

**In short:** let a HorizontalPodAutoscaler own the replica count, on CPU at about 70% of the request, with a cap on how
fast it adds pods.

### What's going on

The autoscaler compares the measured CPU with your target and adds or removes pods. The JVM makes this tricky: a
new JVM runs slower code for its first minutes, so it burns more CPU per request. Once it is ready, the CPU it spends
warming up counts as load and can trigger another round of scaling up, which adds more cold pods.

By default the autoscaler adds pods right away and waits 5 minutes before scaling down.

### Do this

1. Target 60 to 70% CPU, so new pods have room while they warm up.
2. Set `behavior` explicitly: cap how many pods may be added per minute when scaling up and remove at most one
   pod per minute when scaling down.
3. Set `minReplicas` to at least 3 in production.
4. Shorten the warmup with the AOT cache from [step 6 of the JVM guide](/guides/jvm-in-containers/#jvm-aot-cache)
   or warm hot paths in an `ApplicationRunner`, which runs before the pod turns ready.

### When this is not for you

- Services that mostly wait on I/O or consume a queue: CPU is a poor signal. Scale on request rate or queue depth
  with KEDA, which creates its own autoscaler. Never keep both on one Deployment.

<a id="kube-spread"></a>

## 7. How do I keep replicas from failing together?

**In short:** spread replicas across zones strictly and across nodes loosely.

```yaml
topologySpreadConstraints:
  - { maxSkew: 1, topologyKey: topology.kubernetes.io/zone, whenUnsatisfiable: DoNotSchedule,
      labelSelector: { matchLabels: { app.kubernetes.io/name: orders-service } },
      matchLabelKeys: [pod-template-hash] }
```

### What's going on

Three replicas on one node or in one zone fail together when that node or zone goes down. Spread constraints
tell the scheduler to keep the count per zone balanced: 3 replicas land in 3 zones and stay balanced as the
service scales.

`matchLabelKeys: [pod-template-hash]` makes the scheduler count each version separately. Without it, a rollout
counts old and new pods together and can stack the new ones in one zone.

### Do this

1. Add a zone constraint with `maxSkew: 1` and `DoNotSchedule`.
2. Add a node constraint on `kubernetes.io/hostname` with `ScheduleAnyway`, so two replicas avoid one node without
   blocking scheduling.
3. Put `matchLabelKeys: [pod-template-hash]` on both.

### When this is not for you

- A dev cluster with one zone or nodes without the zone label: a strict zone rule can leave pods pending. Relax
  it there.
- Prefer spread constraints to `podAntiAffinity`: a required `podAntiAffinity` caps replicas at the number of nodes.

<a id="kube-scheduled-work"></a>

## 8. Where should scheduled jobs run?

**In short:** short housekeeping in the service with a lock; heavy batch work in a Kubernetes `CronJob`.

### What's going on

A method with `@Scheduled` runs in every replica. With 3 replicas it runs 3 times, which is rarely what you want.
A lock in the database fixes that: every replica tries, one wins. ShedLock is the usual library for it.

Heavy work is different. A batch that runs for minutes competes with requests for CPU and memory. A `CronJob`
gives it its own pod, retries and a hard timeout.

### Do this

1. For short frequent tasks, use `@Scheduled` with ShedLock and the database clock. Set `lockAtMostFor` longer than
   the slowest run and shorter than the interval.
2. For batch work, use a `CronJob` with `concurrencyPolicy: Forbid` and an explicit `timeZone`, reusing the
   service's image and configuration.
3. Make jobs idempotent either way: a job can run more than once.

### When this is not for you

- One replica that will never scale: plain `@Scheduled` works, until the day it scales.

<a id="kube-diagnose"></a>

## 9. Why is my pod not ready?

**In short:** read the pod's events first, then the logs of the container that crashed before, then call the
probe yourself.

```sh
kubectl describe pod <pod>
kubectl logs <pod> -c app --previous
```

### What's going on

A pod that never becomes ready is stuck at one of a few gates. Each gate leaves a different trace. The status
is the first clue:

| Status | Usually | Look at |
| ------ | ------- | ------- |
| `Pending` | No node has room for the requests or a spread rule cannot be met | The events in `kubectl describe pod` |
| `ImagePullBackOff` | A wrong tag or digest, no pull rights or an image for another CPU architecture | The events in `kubectl describe pod` |
| `CrashLoopBackOff` | A missing setting or secret or the database unreachable at startup | `kubectl logs --previous` |
| `OOMKilled`, exit code 137 | The limit is too small for the heap plus native memory | The container's last state, then the [JVM guide](/guides/jvm-in-containers/#jvm-heap-sizing) |
| Running but not ready | The readiness probe fails or times out | The events, then the probe itself |

The `--previous` flag matters. After a crash, plain `kubectl logs` shows the new container, which has not failed
yet.

### Do this

1. Run `kubectl describe pod <pod>` and read the events at the bottom.
2. For a crash, read `kubectl logs <pod> -c app --previous` and the container's last state in the same
   `describe` output.
3. For a failing probe, forward the ports with `kubectl port-forward pod/<pod> 8080 8081` and call `/livez` and
   `/readyz` with `curl -v`.
4. For a ready pod that gets no traffic, list the Service's endpoints with
   `kubectl get endpointslices -l kubernetes.io/service-name=<service>`, then compare the Service selector and port
   name with the pod. Check that a NetworkPolicy admits the caller.
5. For a JVM problem in an image without a shell, attach a debug container that shares the app's processes:
   `kubectl debug -it <pod> --image=<jdk image> --target=app -- jcmd 1 Thread.print`. It needs the right to create
   ephemeral containers and the same user ID as the JVM.

### When this is not for you

- A probe that fails only under load points to thread starvation or long GC pauses, not to the probe itself: see
  step 1 and the [JVM guide](/guides/jvm-in-containers/).
- Spring Security that blocks `/livez` looks exactly like a failing probe: permit the probe paths.

## Put it all together

The app settings live in `application.yaml`; everything else goes in the Deployment and its neighbours.

seconds (step 2).

**Check it:** start the service and run `curl -s localhost:8080/readyz`. It answers `{"status":"UP"}` on the main
port, while Actuator itself listens on 8081.

### In the Deployment

- Probes: `startupProbe` and `livenessProbe` on `/livez`, `readinessProbe` on `/readyz`, all with
  `timeoutSeconds: 2` (step 1).
- `preStop` with `sleep` for 10 seconds and `terminationGracePeriodSeconds: 45` (step 2).
- Memory request equal to the limit, a CPU request and no CPU limit (step 3).
- `maxSurge: 1`, `maxUnavailable: 0`, `minReadySeconds: 10` and no `spec.replicas` (step 4).
- Zone and node spread with `matchLabelKeys: [pod-template-hash]` (step 7).

### Next to the Deployment

- A PodDisruptionBudget with `maxUnavailable: 1` and `unhealthyPodEvictionPolicy: AlwaysAllow` (step 5).
- A HorizontalPodAutoscaler on CPU with explicit `behavior` and `minReplicas: 3` in production (step 6).
- A `CronJob` for batch work, if the service has any (step 8).
