Your Spring Boot service runs fine on your laptop. In Kubernetes it restarts every few hours, takes ages to start
and pauses for no reason. Usually the code is fine: the JVM is guessing the size of a machine it cannot see.

This guide walks through the eight decisions that stop the guessing: memory, CPU, garbage collector and startup.
Each one takes a few minutes and the last section gives you the files to copy.

<a id="jvm-heap-sizing"></a>

## 1. How much memory can the heap take?

**In short:** give the heap 75% of the pod's memory limit and leave the rest for everything else the JVM needs.

```text
-XX:MaxRAMPercentage=75 -XX:InitialRAMPercentage=75
```

### What's going on

Your pod restarts with `OOMKilled`, yet the heap graph never passed 60%. How?

Think of the memory limit as a suitcase. The heap is the biggest thing you pack but not the only one: the JVM
also carries compiled code, class metadata, one stack per thread and network buffers. Kubernetes weighs the whole
suitcase. If the heap takes almost all the space, the rest does not fit and the kernel kills the pod. No error, no
heap dump, just a restart.

<ContainerMemoryDiagram />
<DiagramLegend items={['recommended', 'context', 'failure']} />

The JVM default makes the opposite mistake: it uses only 25%, so a 1 GiB pod gets a 256 MiB heap.

### Do this

1. Set the memory request equal to the limit in the Deployment.
2. Add the two flags above. In a 1 GiB pod that is a 768 MiB heap and 256 MiB for the rest.
3. Add `-XX:+ExitOnOutOfMemoryError`, so a real `OutOfMemoryError` restarts the pod cleanly.
4. Under a load test, confirm the rest fits: start with `-XX:NativeMemoryTracking=summary` and compare its total
   with the container's memory use.

### When this is not for you

- Pods under 1 GiB: the "rest" is a bigger share, so go down to 50 or 60%. At 4 GiB and up, 75 to 80% is fine.
- You want the JVM to give memory back when idle: drop `InitialRAMPercentage` and see step 4 for ZGC.

<a id="jvm-gc-explicit"></a>

## 2. Why did my pod get the slow garbage collector?

**In short:** the JVM picked it because the pod looked small. Always name the collector yourself.

```text
-XX:+UseG1GC
```

### What's going on

The JVM chooses its garbage collector when it starts, based on the machine it thinks it is on. With fewer than
2 CPUs or less than about 1792 MB of memory, it decides the machine is small and picks SerialGC: a single thread
does all the cleanup and your app stops while it works.

A pod with `cpu: 1` or with a 1 GiB limit, falls into this. Nothing in the logs tells you.

### Do this

1. Put `-XX:+UseG1GC` in the image `ENTRYPOINT` (step 5 explains why there).
2. Use the same flag in the AOT training run (step 6) or the cache is rejected.
3. Check what a running pod got:

   ```sh
   java -XX:+PrintFlagsFinal -version | grep -E 'UseG1GC|UseSerialGC'
   ```

   `UseG1GC` must be `true`.

### When this is not for you

- Your workload needs another collector: pick it in step 4 and make that choice explicit too.

<a id="jvm-cpu-count"></a>

## 3. How many CPUs does the JVM think it has?

**In short:** set no CPU limit and tell the JVM its CPU count: the CPU request rounded up, at least 2.

```text
-XX:ActiveProcessorCount=2
```

### What's going on

The JVM sizes a lot by CPU count: garbage collector threads, compiler threads, the common thread pool and the
carriers for virtual threads. Since JDK 19 it reads only the CPU limit, never the request.

So with no limit, it sees the whole node. On a 64-core node, a pod that asked for 2 CPUs gets 13 GC threads and a
common pool of 63. With a limit, the count is right but Kubernetes throttles the pod whenever it bursts and
startup and GC pauses slow down.

The flag fixes the count without the throttling.

### Do this

1. Remove the CPU limit from the Deployment; keep the request.
2. Set `-XX:ActiveProcessorCount` to the request rounded up, at least 2, in the Deployment's
   `JAVA_TOOL_OPTIONS`. The minimum of 2 also keeps G1 from step 2.
3. When you change the CPU request, change the flag with it.

### When this is not for you

- Your cluster requires CPU limits: drop the flag. The JVM reads the limit and you accept the throttling.

<a id="jvm-gc-choice"></a>

## 4. Which garbage collector should I use?

**In short:** G1 for almost every Spring Boot service. Choose another only for a reason you can measure.

### What's going on

A garbage collector balances three things: how long the app pauses, how much work gets done and how much extra
CPU and memory it needs. G1 balances them well for request and response services. Each of the others wins one of
the three by paying with the rest.

| Collector | Flag | Choose it for |
| --------- | ---- | ------------- |
| G1 | `-XX:+UseG1GC` | Request and response services, heaps from 512 MB to 32 GB |
| Generational ZGC | `-XX:+UseZGC` | Latency targets where pauses must stay under 1 ms |
| Generational Shenandoah | `-XX:+UseShenandoahGC -XX:ShenandoahGCMode=generational` | Another option with short pauses, a product feature since JDK 25 |
| Parallel | `-XX:+UseParallelGC` | Batch jobs, where throughput matters and pauses do not |
| Serial | `-XX:+UseSerialGC` | Tiny sidecars and CLIs, by choice, never by accident |

### Do this

1. Start with G1.
2. Switch only when a load test shows the need: pauses that break your latency target (ZGC) or a batch job that
   should finish sooner (Parallel).
3. When you switch, retrain the AOT cache with the new collector (step 6). In JDK 25, a ZGC service must train
   its cache with ZGC.

### When this is not for you

- Old advice about ZGC without generations: that mode was removed in JDK 24.
- Compact object headers (`-XX:+UseCompactObjectHeaders`) save heap in services that allocate a lot. Turn them on
  only after a load test and in the training run too.

<a id="jvm-flag-placement"></a>

## 5. Where do JVM flags go: the image or the Deployment?

**In short:** flags that belong to the image go in the `ENTRYPOINT`. Sizing goes in `JAVA_TOOL_OPTIONS` from the
Deployment.

### What's going on

There are two places to put JVM flags and they behave differently. The `ENTRYPOINT` is baked into the image.
`JAVA_TOOL_OPTIONS` is an environment variable and when a Deployment sets it, it replaces the image's value
completely. It never merges.

So a GC flag kept in `JAVA_TOOL_OPTIONS` disappears the day someone adds a sizing flag to the Deployment.

| Where | What | Why |
| ----- | ---- | --- |
| `ENTRYPOINT` | `-XX:+UseG1GC`, `-XX:AOTCache=/app/app.aot`, `-XX:ErrorFile=/tmp/hs_err_pid%p.log` | They must match the image and a Deployment cannot drop them |
| `JAVA_TOOL_OPTIONS` | Memory percentages, `ActiveProcessorCount`, `ExitOnOutOfMemoryError`, `java.io.tmpdir=/tmp` | They change per environment |

### Do this

1. Put the image flags in the Dockerfile `ENTRYPOINT`.
2. Put sizing in the Deployment's `JAVA_TOOL_OPTIONS`.
3. Mount `/tmp` as an `emptyDir` and run with a read-only root filesystem. The crash log goes to `/tmp`, because
   the default location is read-only.
4. Never set `command:` in the Deployment: it replaces the `ENTRYPOINT`. Use `args:` or nothing.

### When this is not for you

- It always applies. The cost: changing the collector needs a new image. That is the point, because the AOT cache
  was trained with that collector.

<a id="jvm-aot-cache"></a>

## 6. How do I make the service start faster?

**In short:** train an AOT cache while building the image and check in CI that the JVM really uses it.

```text
-XX:AOTCache=/app/app.aot
```

### What's going on

When a Spring Boot service starts, the JVM spends its first seconds loading and linking thousands of classes, the
same ones every time. JDK 25 can record that work once, during the image build and reuse it on every start. In
this repository's test service, startup on 2 CPUs drops from about 4.7 to 2.6 seconds.

The catch: if the cache does not match the JVM that runs it, the JVM quietly ignores it. A rejected cache looks
exactly like no cache, so you have to test for it.

<ImageBuildTimelineDiagram />
<DiagramLegend items={['recommended', 'context', 'failure']} />

### Do this

1. In the image's runtime stage, extract the jar with `-Djarmode=tools extract --layers` (without `--launcher`).
2. Run the app once to train the cache. It stops by itself after creating its beans:

   ```sh
   java -XX:+UseG1GC -XX:AOTCacheOutput=/app/app.aot -Dspring.context.exit=onRefresh -jar /app/application.jar
   ```

3. Add `-XX:AOTCache=/app/app.aot` to the `ENTRYPOINT`.
4. In CI, prove it is used: `-XX:AOTMode=on` exits with an error if the cache is unusable and `-Xlog:aot` prints
   `Opened AOT cache` when it loads.

### When this is not for you

- Beans that connect to a database or broker while starting: switch them off for the training run with a `-D`
  property or training fails.
- A new JDK build, collector or class path needs a new cache. Training in the image build handles that.
- The cache speeds up startup only. It does not make requests faster.

<a id="jvm-startup-options"></a>

## 7. What about native image, CRaC and Spring AOT?

**In short:** use the AOT cache by default. The other options start faster still but cost much more.

### What's going on

Every option here promises faster startup. They differ in what you pay: build time and rules your app must
follow at runtime. Teams often pick the most impressive number and pay for it for years.

| Option | What you pay | Use it for |
| ------ | ------------ | ---------- |
| JDK AOT cache | A training run in the image build | Every JDK 25 service, by default |
| Spring AOT on the JVM | Profiles and conditions fixed at build time | Services already compatible with native image |
| AOT cache plus Spring AOT | Both of the above | JVM services that scale to zero or in sudden bursts |
| GraalVM native image | Minutes and gigabytes per build, no JIT, no agents | Functions, CLIs, sidecars |
| CRaC | A special JDK, Linux capabilities, secrets inside the snapshot | Specialist cases with vendor support |

### Do this

1. Services that stay up for days: the AOT cache from step 6.
2. JVM services that scale to zero: add Spring AOT.
3. Functions, CLIs and sidecars: native image.
4. Anything else: measure first, then decide.

### When this is not for you

- Startup is not a problem for you: stop at step 6. Every option beyond it adds cost.

<a id="jvm-startup-probe"></a>

## 8. How long should Kubernetes wait for startup?

**In short:** measure startup on your smallest node and give the `startupProbe` about three times that.

### What's going on

Kubernetes kills a pod that does not start within the `startupProbe` budget. A budget guessed on a laptop is too
short for the smallest node in production, where startup is slowest. A huge budget has the opposite problem: it
hides a pod that hangs forever.

<PodTopologyDiagram />
<DiagramLegend items={['recommended', 'context', 'optional']} />

### Do this

1. Measure the slowest normal startup (p99), with the AOT cache, on the smallest node type you run.
2. Set `periodSeconds: 5` and a `failureThreshold` that covers about three times that. For 10 seconds, that is
   30 seconds, so `failureThreshold: 6`.
3. Probe `/livez`, which never checks the database or other dependencies.
4. Measure again after a JDK, Spring Boot or node type change.

### When this is not for you

- You must detect a stuck pod within seconds: keep the budget tight and accept a few restarts on slow nodes.

## Put it all together

Everything above lands in two places: the image and the Deployment.

### The image

The last stage of the Dockerfile applies steps 1, 2, 5 and 6. It sets the sizing defaults, trains the AOT cache
and starts the JVM with G1 and the cache.

<Recipe id="jvm-runtime-stage" path="fixtures/single-hexagonal/Dockerfile" start="FROM eclipse-temurin:25.0.4.1_1-jre-noble" end="ENTRYPOINT [" lang="dockerfile" />

**Check it:** run the image with `-e JDK_JAVA_OPTIONS=-Xlog:aot`. The log shows `Opened AOT cache /app/app.aot`,
so the cache is in use.

### In the Deployment

- Memory request equal to the limit (step 1).
- A CPU request and no CPU limit (step 3).
- `JAVA_TOOL_OPTIONS` with the memory flags and `-XX:ActiveProcessorCount` (steps 1, 3 and 5). It replaces the
  image's value, so repeat the memory flags there.
- A `startupProbe` on `/livez`, sized from measured startup (step 8).
- No `command:`, so the image's `ENTRYPOINT` stays (step 5).
