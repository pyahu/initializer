An order is paid, the service publishes "send the receipt" and moves on. The receipt never arrives. The broker
restarted a second after the publish, the message lived only in memory and nobody noticed. A week later the
opposite happens: one malformed message fails, goes back to the queue, fails again and keeps a consumer busy all
night.

This guide sets up RabbitMQ with Spring AMQP on Spring Boot 4.1 so a message is either safely stored or the
publisher knows it is not. A message that cannot be handled ends up somewhere you can look at it.

## 1. When should I use RabbitMQ instead of Kafka?

**In short:** use RabbitMQ for work that someone must do once, like tasks and commands. Use Kafka for facts many
services read, replay and keep.

### What's going on

RabbitMQ is a post office. A message goes to an exchange, which routes it to one or more queues by a key. A
consumer takes it, does the work and acknowledges it. Once acknowledged, the message is gone.

Kafka is a newspaper archive. Events stay in a log for days, every reader keeps its own place and a new reader can
start from the beginning.

So RabbitMQ shines when each message is a job: send an email, resize an image, charge a card. It routes flexibly
and acknowledges each message on its own, so one slow job does not block the next.

### Do this

1. Choose RabbitMQ for task queues, commands to one service and routing by key or pattern.
2. Choose Kafka for events that several services consume or that you may need to replay
   ([Kafka with the outbox](/guides/kafka/)).
3. Add `spring-boot-starter-amqp`. The Spring Boot 4.1.1 BOM manages Spring AMQP 4.1.1 and the RabbitMQ Java
   client `amqp-client` 5.30.0.

### When this is not for you

- You need to replay history or rebuild a read model: a queue forgets a message once it is acknowledged.
- You need strict order across all messages: RabbitMQ keeps order per queue, not across consumers working in
  parallel.

<a id="rmq-quorum-queues"></a>

## 2. Which kind of queue should I declare?

**In short:** a durable quorum queue, unless you have a measured reason for something else.

```text
x-queue-type: quorum
```

### What's going on

A classic queue lives on one node. If that node dies, the queue is unavailable until it comes back. The old fix,
classic mirrored queues, was deprecated in 2021 and removed in RabbitMQ 4.0.

A quorum queue keeps copies on several nodes and needs a majority of them to agree before it accepts a message.
Lose one node of three and the queue keeps working. It also brings features this guide relies on: a delivery
limit for poison messages and safer dead lettering.

### Do this

1. Declare queues as durable with the argument `x-queue-type: quorum`.
2. Run at least three broker nodes, so a majority survives one failure.
3. Declare queues, exchanges and bindings in code as `Queue`, `Exchange` and `Binding` beans, so every environment
   gets the same topology.
4. Leave `spring.rabbitmq.listener.simple.missing-queues-fatal` at its default, `true`: a consumer whose queue is
   missing should fail loudly.

### When this is not for you

- Short lived reply queues and temporary queues: those can stay classic and exclusive.
- Huge fan out or replay over a stream of events: RabbitMQ streams or Kafka fit better.

<a id="rmq-publisher-confirms"></a>

## 3. How do I know the broker really has my message?

**In short:** turn on publisher confirms and returns, then wait for the confirm before you treat the message as
sent.

```yaml
spring.rabbitmq.publisher-confirm-type: correlated
spring.rabbitmq.publisher-returns: true
spring.rabbitmq.template.mandatory: true
```

### What's going on

By default, `convertAndSend` hands the message to the network and returns. If the broker restarts or no queue is
bound for that routing key, the message disappears and your code never hears about it.

A publisher confirm is the broker's receipt: it says "stored". For a quorum queue that means stored on a
majority of nodes. A return is the broker saying "I had nowhere to put this". Together they turn silent loss into
something your code can see and act on.

### Do this

1. Set the three properties above. `correlated` lets you match each confirm to the message you sent.
2. Send with a `CorrelationData` and wait on its future, `correlationData.getFuture()`, with a timeout.
3. If the confirm is a nack or the message came back as returned, treat the send as failed: retry it or fail the
   request.
4. Use one connection per application and let Spring cache channels on it. The default cache mode is `channel`;
   raise `spring.rabbitmq.cache.channel.size` only if you see channels being opened and closed under load.

### When this is not for you

- Fire and forget metrics or notifications where losing a few is fine: skip the wait and keep the throughput.
- You publish as part of a database transaction: a confirm still does not make the two atomic. Use an outbox
  ([Kafka with the outbox](/guides/kafka/) explains the pattern).

<a id="rmq-acks-prefetch"></a>

## 4. How many messages should a consumer take at once?

**In short:** acknowledge after the work is done and size the prefetch to how long one message takes.

```yaml
spring.rabbitmq.listener.simple.prefetch: 10
```

### What's going on

The broker pushes messages to a consumer ahead of time. The prefetch is how many unacknowledged messages one
consumer may hold. Spring AMQP's default is 250.

For fast messages that is good: the consumer never waits. For slow ones it is a trap. One consumer grabs 250 jobs
that take a minute each, while a second consumer sits idle. On a restart all 250 go back to the queue.

Spring acknowledges for you when the listener method returns without an exception, which is the default `auto`
mode. That is what you want: the message is only gone once the work is done.

### Do this

1. Keep the default acknowledge mode. Do not acknowledge before the work is finished.
2. Lower `spring.rabbitmq.listener.simple.prefetch` for slow work, for example 1 to 10 for jobs that take
   seconds.
3. Scale with `spring.rabbitmq.listener.simple.concurrency` and `max-concurrency` or with more pods.
4. Finish each message well within the broker's consumer timeout, 30 minutes by default. A consumer that holds a
   message longer has its channel closed and the message is delivered again.

### When this is not for you

- Tiny, fast messages at high rates: a large prefetch is fine. RabbitMQ's docs note that very large values
  add little over a few hundred.
- Jobs that take longer than the consumer timeout: split them or track progress elsewhere and acknowledge
  early on purpose.

<a id="rmq-retries-dlx"></a>

## 5. What happens when a message keeps failing?

**In short:** retry a few times with backoff, then send it to a dead letter queue. Never requeue it forever.

```yaml
spring.rabbitmq.listener.simple.retry.enabled: true
spring.rabbitmq.listener.simple.retry.max-retries: 3
spring.rabbitmq.listener.simple.retry.initial-interval: 1s
spring.rabbitmq.listener.simple.retry.multiplier: 2
```

### What's going on

When a listener throws, Spring rejects the message and by default asks the broker to requeue it. A message that
can never succeed, a poison message, then loops: delivered, failed, requeued, delivered again.

RabbitMQ 4.0 limits that damage. A quorum queue counts failed deliveries and stops at 20 by default; after that it
drops the message or dead letters it if the queue has a dead letter exchange. Dropping is the silent part you
want to avoid.

With listener retry on, Spring retries in the consumer with backoff. When the retries run out, Spring Boot's
default recoverer rejects the message without requeueing, so it goes straight to the dead letter exchange.

### Do this

1. Turn on listener retry with a small `max-retries` and a backoff. In Spring Boot 4, `max-retries` replaces the
   old `max-attempts`.
2. Give every work queue a dead letter exchange and a dead letter queue, through a policy or queue arguments.
3. On quorum queues, set `dead-letter-strategy` to `at-least-once`, so a message is not lost while it moves to the
   dead letter queue. It needs the `reject-publish` overflow setting on the source queue.
4. Alert on messages in dead letter queues and keep a way to inspect and replay them.

### When this is not for you

- Failures caused by a downstream outage: a few quick retries will not help. Let the message go back later or
  pause the consumer instead of burning through the retries.
- Retries block the consumer thread while they wait. For long backoffs, use a delay queue with a TTL that dead
  letters back to the work queue.

<a id="rmq-idempotent"></a>

## 6. Why was the same message processed twice?

**In short:** because delivery is at least once. Make every consumer safe to run twice on the same message.

### What's going on

RabbitMQ with confirms and acknowledgements guarantees that a message arrives at least once, not exactly once. A
consumer can finish the work and crash before its acknowledgement reaches the broker. The broker then delivers the
message again, to the same or another consumer.

This is not a bug to fix in the broker. It is the price of never losing a message and the consumer has to pay
it.

### Do this

1. Give every message a unique id when you publish it, in the `messageId` property.
2. In the consumer, record the ids you have processed in the same database transaction as the work. Skip a
   message whose id is already there.
3. Prefer operations that are naturally safe to repeat, like "set status to paid" instead of "add 10 to the
   balance".

### When this is not for you

- The work is already idempotent, like overwriting a cache entry: the id table adds nothing.
- Duplicates do not matter at all, like a best effort notification: accept them and keep it simple.

<a id="rmq-limits"></a>

## 7. How do I stop a queue from growing forever?

**In short:** give queues a maximum length and messages a time to live, chosen on purpose.

### What's going on

A queue is a buffer. If consumers stop or slow down, it grows until the broker runs short of memory or disk. Then publishers everywhere slow down or block. One forgotten queue can hurt every service on the broker.

Limits turn that into a decision. A TTL says how long a message is still worth processing. A maximum length says
what happens when the buffer is full: by default the oldest messages are dropped (`drop-head`) or new publishes
are refused (`reject-publish`), which a publisher with confirms will see.

### Do this

1. Set `x-max-length` or `x-max-length-bytes` on queues that can fill up, through a policy.
2. Prefer `overflow: reject-publish` for work you must not lose, so the publisher learns about it. Quorum queues
   support `drop-head` and `reject-publish`.
3. Set a message TTL where old work is useless, like a password reset email after an hour.
4. Send expired and dropped messages to the dead letter exchange when you need to know about them.

### When this is not for you

- Queues where every message must be processed, however late: no TTL; scale consumers instead.
- Short bursts that consumers absorb quickly: monitor the depth before adding limits.

<a id="rmq-monitoring"></a>

## 8. What should I watch in production?

**In short:** queue depth, unacknowledged messages, consumers per queue and dead letter queues, from the broker's
Prometheus plugin.

### What's going on

A queue tells you how the system is doing. Depth growing means consumers cannot keep up. Many unacknowledged
messages mean consumers are stuck or the prefetch is too high. A queue with zero consumers means a service is down
or failed to start. Messages in a dead letter queue mean work is failing.

RabbitMQ exposes all of this in Prometheus format through its built in `rabbitmq_prometheus` plugin. Spring
can add traces around publish and consume, so a message is part of the same trace as the request that sent it.

### Do this

1. Enable the `rabbitmq_prometheus` plugin and scrape it.
2. Alert on depth growing for several minutes, on any queue with zero consumers and on any message in a dead
   letter queue.
3. Turn on `spring.rabbitmq.template.observation-enabled` and `spring.rabbitmq.listener.simple.observation-enabled`
   (both off by default) to trace messages ([Observability](/guides/observability/)).
4. Set `spring.rabbitmq.requested-heartbeat` and `connection-timeout` on purpose, so a dead connection is noticed.

### When this is not for you

- A managed RabbitMQ that already exports these metrics: use its dashboards and alert on the same signals.

## Put it all together

No tested example service uses RabbitMQ yet, so the pieces are lists.

### In application.yaml

- `spring.rabbitmq.publisher-confirm-type: correlated`, `publisher-returns: true` and
  `template.mandatory: true` (step 3).
- `listener.simple.prefetch` sized to the work (step 4).
- `listener.simple.retry.enabled: true` with a small `max-retries` and a backoff (step 5).
- `template.observation-enabled` and `listener.simple.observation-enabled` set to `true` (step 8).

### In the code

- Queues declared as durable quorum queues, with exchanges and bindings as beans (step 2).
- Every publish with a `CorrelationData` and a `messageId`, waiting on the confirm (steps 3 and 6).
- Consumers that record processed message ids in the same transaction as the work (step 6).

### On the broker

- At least three nodes (step 2).
- Policies for dead lettering with `at-least-once`, maximum length and TTL (steps 5 and 7).
- The `rabbitmq_prometheus` plugin with alerts on depth, consumers and dead letters (step 8).
