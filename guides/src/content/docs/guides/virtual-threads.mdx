You turn on virtual threads with one property and the benchmark looks great. Then production gets slower: the
database pool is always full, a service you call starts failing and the slowest requests take longer than before.

This guide explains why that happens and puts the limits back where they belong. Virtual threads are a good
default for most Spring Boot services, as long as you know what they stop doing for you.

<a id="vt-enable"></a>

## 1. Should I turn on virtual threads?

**In short:** yes, for services that spend their time waiting on a database, a broker or other services. Keep CPU
heavy work elsewhere.

```yaml
spring.threads.virtual.enabled: true
```

### What's going on

A normal Java thread is expensive, so Tomcat keeps a pool of 200 of them. A virtual thread is cheap: the JDK runs
thousands of them on a few real threads, called carriers, about one per CPU. When a virtual thread waits on the
network, its stack moves to the heap and the carrier runs another one.

Think of a restaurant. Before, each table had its own waiter standing there while the kitchen cooked. Now a few
waiters serve every table and only walk over when there is something to do.

The property is off by default. Turning it on makes Spring Boot 4.1 handle web requests, `@Async` tasks and
`@Scheduled` tasks on virtual threads and use them in the message listeners it configures for Kafka and RabbitMQ.

### Do this

1. Set `spring.threads.virtual.enabled: true` in `application.yaml`.
2. Confirm it: log `Thread.currentThread()` in a controller. A virtual thread prints as
   `VirtualThread[#…]/runnable@ForkJoinPool-1-worker-…`.
3. Read steps 2 and 3 before you deploy. They are why this step is safe.

### When this is not for you

- The service mostly computes (pricing, parsing, compression): it gains little. See step 4.
- The service is already reactive end to end with WebFlux and reactive drivers: keep it.
- Heavy native code through JNI: native frames still pin a carrier (step 8).

<a id="vt-resource-limits"></a>

## 2. Why did latency get worse after I turned them on?

**In short:** the 200 Tomcat threads used to limit how much work hit your database at once. Now nothing does, so
size the connection pool from the database and make waiting fail fast.

```yaml
spring.datasource.hikari:
  maximum-pool-size: 10
  minimum-idle: 10
  connection-timeout: 3000
```

### What's going on

With a pool of 200 threads, at most 200 requests ran at once. Nobody chose that number to protect the database,
but it did. With virtual threads every request runs, so 2,000 requests can line up for 10 database connections.
The pool becomes the queue. Requests wait there for up to 30 seconds, HikariCP's default.

Virtual threads remove the thread limit. They do not add database connections or make a slow service faster.

### Do this

1. Size `maximum-pool-size` from what the database allows, shared by every pod, not from the number of threads.
   Keep the pool fixed: `minimum-idle` equal to the maximum.
2. Set `connection-timeout` to 3 seconds, so a request that cannot get a connection fails fast instead of piling up.
3. Watch `hikaricp.connections.pending`. It rises when requests wait for the pool.
4. Load test before and after with the same pool size and compare p95 and p99, not only throughput.

### When this is not for you

- Heap use grows too: each waiting virtual thread keeps its stack on the heap. Leave heap headroom and cap the
  concurrency.
- `server.tomcat.threads.max` no longer does anything with virtual threads. `server.tomcat.max-connections`
  (8192 by default) still applies.

<a id="vt-downstream-limits"></a>

## 3. How do I keep a slow service from drowning in my calls?

**In short:** put an explicit limit on how many calls you make at once to each service and a timeout on every call.

```java
@ConcurrencyLimit(50)
RiskScore score(String id) { ... }
```

### What's going on

The same thing that happened to the database happens to every service you call. Before, 200 threads meant at most
200 calls in flight. Now a traffic spike becomes thousands of calls at once to a service that may handle a hundred.
It slows down, your calls wait longer, more calls pile up and both sides fall over.

Spring Framework 7 adds `@ConcurrencyLimit`: at most N calls run through a method at the same time while the rest wait.

### Do this

1. Turn the annotations on with `@EnableResilientMethods` on a configuration class.
2. Put `@ConcurrencyLimit(n)` on the client method for each downstream service, with `n` from what that service can
   take.
3. Give every outbound call a connect timeout and a read timeout. The limit stops the flood; the timeouts stop one
   slow call from holding a slot forever.
4. Limit retries and add jitter: retries times replicas times layers multiply the load on a service that is
   already struggling.

### When this is not for you

- One limit shared by several methods: use a `Semaphore` and release it in a `finally` block.
- You also want metrics, a circuit breaker and retries in one place: a Resilience4j bulkhead does that, with an extra
  dependency. Check its Spring Boot 4 support first.

<a id="vt-cpu-work"></a>

## 4. Where does CPU heavy work go?

**In short:** on a separate pool of platform threads, sized to the cores. Give the JVM at least 2 CPUs so it has
at least 2 carriers.

```java
@Bean(destroyMethod = "shutdown")
ExecutorService cpuPool() {
    return Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors());
}
```

### What's going on

A virtual thread only lets go of its carrier when it waits. It is never paused to let another one run. So a request
that computes for a second holds a carrier for that whole second. With 2 carriers, two such requests stop
everything else.

The number of carriers comes from the CPU count the JVM sees. A pod with a CPU limit of `500m` rounds up to 1 CPU,
so it gets 1 carrier and behaves like a single threaded server.

### Do this

1. Move the heavy part of a request to a fixed pool of platform threads, sized to the cores and wait for its result.
2. Give the pod a CPU request of at least 1. Then set either `-XX:ActiveProcessorCount` of 2 or more with no
   CPU limit or a CPU limit of at least 2. The JVM in containers guide explains the flag.
3. Never run blocking I/O on `ForkJoinPool.commonPool()`. It is shared by the whole JVM and sized for CPU work.

### When this is not for you

- The service never does heavy computation on a request: skip the extra pool but keep the CPU count right.

<a id="vt-executors"></a>

## 5. Why does my @Async code still run on old threads?

**In short:** a task executor bean you declared yourself wins over Boot's. Remove it or make it use virtual threads
on purpose.

### What's going on

With virtual threads on, Boot configures the executor behind `@Async` to start one virtual thread per task and the
scheduler behind `@Scheduled` to use virtual threads too. It only does this when you have not declared your own.
A `ThreadPoolTaskExecutor` bean from an old configuration keeps `@Async` on platform threads named `task-1`,
`task-2` and so on.

The old `spring.task.execution.pool.*` settings are ignored with virtual threads. The `simple` ones apply instead.

### Do this

1. Look for your own `Executor` or `TaskExecutor` beans and remove the ones you do not need.
2. Cap concurrent `@Async` tasks with `spring.task.execution.simple.concurrency-limit` and concurrent
   `@Scheduled` tasks with `spring.task.scheduling.simple.concurrency-limit`.
3. Choose what happens at the cap: by default the caller waits; with
   `spring.task.execution.simple.reject-tasks-when-limit-reached: true` the task is rejected.
4. For an app with no web server, such as a scheduler or a message listener, set `spring.main.keep-alive: true`.
   Virtual threads are daemon threads, so without it the app exits right after startup.

### When this is not for you

- Work that must not be lost: `@Async` tasks die with the pod. Use a queue or an outbox instead.

<a id="vt-context"></a>

## 6. Why do my logs lose the trace ID in async work?

**In short:** the logging context, the security context and the transaction belong to one thread. Carry them over
explicitly when work moves to another thread.

### What's going on

MDC, Spring Security's `SecurityContextHolder` and transaction state are stored per thread, virtual or not. When
you hand work to another thread with `@Async`, `CompletableFuture.supplyAsync` or your own executor, the new thread
starts empty: log lines lose the trace ID and the user. The call starts a new trace.

Transactions never cross threads. An `@Async @Transactional` method opens a new, separate transaction.

### Do this

1. On Spring executors, set a `TaskDecorator` that copies the context into the task.
2. On your own executors, wrap them with Micrometer context propagation: `ContextExecutorService.wrap(executor,
   ContextSnapshotFactory.builder().build())`. It carries MDC and the trace context.
3. For work that must run after a commit, use `@TransactionalEventListener(phase = AFTER_COMMIT)` or an outbox when
   it must be guaranteed.

### When this is not for you

- New code that passes data down a call chain: `ScopedValue` is final in Java 25 (JEP 506). Spring's own context
  propagation still uses `ThreadLocal` today.
- Caches kept in a `ThreadLocal` (formatters, buffers) stop helping, because virtual threads are not reused. Use
  objects that are safe to share.

<a id="vt-fan-out"></a>

## 7. How do I call two services at once with one deadline?

**In short:** submit both calls to one long lived executor, wait with one shared deadline and cancel what is late.

```java
Future<RiskScore> risk = fanOut.submit(() -> riskClient.score(id));
RiskScore score = await(risk, deadline, RiskScore.UNKNOWN);   // get(remaining time), cancel(true) on timeout
```

### What's going on

Calling two services one after the other adds their times. Calling them at once on virtual threads is cheap. But
two common ways to add a deadline do not work:

- A timeout on a `CompletableFuture` (`orTimeout`, `completeOnTimeout`) only completes the future. The call keeps
  running and keeps its connection.
- A `try (var vts = Executors.newVirtualThreadPerTaskExecutor())` block waits for every task when it closes, so your
  fallback still comes back only when the slowest call ends.

### Do this

1. Create one executor bean with `Executors.newVirtualThreadPerTaskExecutor()`, wrapped with
   `ContextExecutorService.wrap` from step 6.
2. Compute one deadline for the whole fan out, such as 500 ms. Wait on each `Future` with
   `get(remaining, NANOSECONDS)`.
3. On a timeout or an error, call `cancel(true)` to interrupt the virtual thread and use a fallback value.
4. Keep connect and read timeouts on every client anyway. They bound the work; the deadline bounds the caller.

### When this is not for you

- `StructuredTaskScope` does this more neatly but it is still a preview in JDK 25 (JEP 505). Fine for experiments,
  not for production code that must compile without `--enable-preview`.
- Whether an HTTP client turns the interrupt into a clean failure depends on the client. Check yours.

<a id="vt-pinning"></a>

## 8. Is synchronized still a problem?

**In short:** no, not on Java 25. Native code still pins a carrier, so check once under load with JFR.

```sh
jfr print --events jdk.VirtualThreadPinned /tmp/app.jfr
```

### What's going on

A pinned virtual thread cannot leave its carrier while it waits, so the carrier sits idle. Older advice says to
replace every `synchronized` block for this reason. Since JDK 24 (JEP 491), `synchronized` no longer pins.

Two cases still do: native frames on the stack (a call through JNI) and class initialization.

### Do this

1. Keep `synchronized`. Use `ReentrantLock` only when you need `tryLock`, a timeout or interruption.
2. Under load, record JFR for a minute: `jcmd <pid> JFR.start duration=60s filename=/tmp/app.jfr`.
3. Look for `jdk.VirtualThreadPinned` events. On JDK 25 only native frames or class initialization should appear.
4. For a thread dump that includes virtual threads, use
   `jcmd <pid> Thread.dump_to_file -format=json /tmp/threads.json`. `jstack` does not list them.

### When this is not for you

- Old flags: `-Djdk.tracePinnedThreads` was removed in JDK 24. Use JFR.

## Put it all together

Virtual threads are one line of configuration; the limits around them live in your code and in the Deployment.

### The setting

The example service turns virtual threads on in `application.yaml` (step 1).

<Recipe id="vt-application-yaml" path="fixtures/single-hexagonal/src/main/resources/application.yaml" start="threads:" end="enabled: true" lang="yaml" />

**Check it:** log `Thread.currentThread()` in a controller and look for `VirtualThread[#…]` in the output.

### In the code

- A HikariCP pool sized from the database budget, with `connection-timeout: 3000` (step 2).
- `@EnableResilientMethods` and a `@ConcurrencyLimit` on each downstream client, with timeouts (step 3).
- A fixed platform pool for CPU heavy work (step 4).
- No stray executor beans; `spring.main.keep-alive: true` in apps without a web server (step 5).
- A context wrapped executor for async work and fan out (steps 6 and 7).

### In the Deployment

- A CPU request of at least 1, then either `-XX:ActiveProcessorCount` of at least 2 with no CPU limit or a CPU
  limit of at least 2 (step 4).
- Heap headroom in `MaxRAMPercentage` for the stacks of waiting virtual threads (step 2).
