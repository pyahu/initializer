The payments service did not go down. It just got slow. Within a minute your own service stops answering: every
request is stuck waiting on payments and the retries you added to be safe triple the load on a service that is
already struggling.

This guide sets a bound on every part of an outbound call: which client to use, how long to wait, how many calls
to allow, when to retry and how to see it all. Each step takes a few minutes and the last section shows where
everything goes.

<a id="http-client-choice"></a>

## 1. Which HTTP client should I use?

**In short:** `RestClient`, behind an HTTP Service Client interface. Use `WebClient` only in reactive code and
write no new `RestTemplate` code.

### What's going on

Spring has three HTTP clients. `RestTemplate` is the old one: the Spring team plans to deprecate it in
Framework 7.1 and remove it in 8.0. `WebClient` is reactive and adding WebFlux to a Spring MVC app just to get a
client brings in a second stack. `RestClient` is the blocking client where new features land and it works well
with virtual threads.

On top of it, you rarely write calls by hand. You describe the other service as a Java interface with
`@HttpExchange` methods and Spring builds the client for you. Framework 7 puts these interfaces into groups with
`@ImportHttpServices`: one group per downstream system, one `RestClient` per group. Boot 4 configures each group
from properties under `spring.http.serviceclient.<group>`.

### Do this

1. Add `spring-boot-starter-restclient`. Boot 4 moved the client support into its own starter.
2. Write one interface per downstream API, with `@HttpExchange` methods and URI variables such as `{id}`.
3. Register one group per downstream system and take its `base-url` from configuration:

   ```java
   @ImportHttpServices(group = "payments", types = PaymentsClient.class)
   ```

4. For calls between services, set `redirects: dont-follow` and reject any 3xx answer with a status handler.
   `dont-follow` alone does not make a 302 an error: the client can return an empty or decoded body as if the call
   worked.

### When this is not for you

- A reactive WebFlux app: use `WebClient`.
- Existing `RestTemplate` code keeps working. Move it to `RestClient` when you touch it: both share the same request
  factories, interceptors and converters.

<a id="http-timeouts"></a>

## 2. Which timeouts does every call need?

**In short:** three of them: connect, read and the wait for a free connection. Set all three on every client.

```yaml
spring.http.clients:
  connect-timeout: 2s
  read-timeout: 5s
```

### What's going on

A service that is down is easy: the call fails at once. A service that is slow is the real danger. With no read
timeout, every request thread waits on it and with virtual threads thousands of requests pile up instead of
hundreds.

Think of a phone call. The connect timeout is how long you let it ring. The read timeout is how long you wait in
silence for an answer. The third one is the queue for a free phone line: how long you wait for a pooled connection
before you can even dial.

Boot 4.1 has properties for the first two: `spring.http.clients.*` for every client and
`spring.http.serviceclient.<group>.*` for one group. A group value you leave out falls back to the global one. The
third has no property: step 3 sets it in code.

### Do this

1. Set `connect-timeout` and `read-timeout` under `spring.http.clients`.
2. Set tighter values per group, such as `connect-timeout: 1s` and `read-timeout: 3s` for payments.
3. Choose the HTTP library on purpose with `spring.http.clients.imperative.factory: http-components`. Otherwise Boot
   detects one from the class path: Apache HttpClient 5, then Jetty, Reactor Netty, the JDK `HttpClient` and last
   `SimpleClientHttpRequestFactory`. With only the web and client starters you get the JDK client.
4. Upgrading from Boot 3: the old `spring.http.client.*` names are deprecated. Rename them to `spring.http.clients.*`
   or your timeouts are silently ignored.

### When this is not for you

- `WebClient` on Reactor Netty: its pool wait is `pendingAcquireTimeout`, 45 seconds by default, set through a
  `ConnectionProvider` in code.

<a id="http-pool"></a>

## 3. Why do calls wait minutes for a connection?

**In short:** Apache HttpClient keeps only 5 connections per host by default and waits up to 3 minutes for a free
one. Make the pool bigger and cap the wait.

### What's going on

Apache HttpClient 5 allows 25 connections in total and 5 per host. If 50 calls to the payments service arrive at
once, 45 of them wait for one of those 5 connections, for up to 3 minutes. The read timeout does not count this
wait, so it shows up as latency nobody can explain.

Boot has no property for the pool size or for this wait. The JDK client has the opposite problem: it has no pool
limit at all, so nothing stops a burst from opening hundreds of connections.

### Do this

1. Add `org.apache.httpcomponents.client5:httpclient5`.
2. Size the pool and cap the wait with a customizer bean, shown below.

```java
@Bean
ClientHttpRequestFactoryBuilderCustomizer<HttpComponentsClientHttpRequestFactoryBuilder> httpComponentsPool() {
    return (builder) -> builder
        .withConnectionManagerCustomizer((pool) -> pool.setMaxConnTotal(128).setMaxConnPerRoute(64))
        .withConnectionConfigCustomizer((c) -> c.setTimeToLive(TimeValue.ofMinutes(5)))
        .withDefaultRequestConfigCustomizer((r) -> r.setConnectionRequestTimeout(Timeout.ofMilliseconds(500)));
}
```

3. Keep connections per host at or above the concurrency limit from step 7, so the limit decides and a rejection is
   explicit instead of a silent wait.
4. Keep the wait for a connection between 0.5 and 1 second.

### When this is not for you

- You use the JDK client: there is no pool to size. Bound the calls with the limit from step 7 instead.
- You want pool metrics: Boot does not bind them for Apache. Micrometer has a binder but you must build the
  connection manager yourself and then own its TLS and timeout settings.

<a id="http-deadline"></a>

## 4. Does a read timeout stop a slow call?

**In short:** not always. With Apache HttpClient the read timeout only measures silence between packets. For a hard
limit per call, use the JDK client or cancel the call yourself.

### What's going on

Each library reads `read-timeout` differently. Apache HttpClient turns it into a socket timeout: the time allowed
between two packets. A server that sends one byte every 500 ms kept a call running for 4.1 seconds under a 1 second
read timeout. The JDK client treats it as a deadline from sending the request to closing the response and the
same slow server failed the call after 1.02 seconds.

Retries do not fix this. The `timeout` of `@Retryable` is checked between attempts: it stops a new attempt from
starting but never interrupts the one in flight. So the worst case is the retry timeout plus one full attempt.

### Do this

1. Budget it: retry `timeout` plus connect plus read timeout must stay under your caller's own timeout.
2. Where one call needs a hard deadline, use the JDK client for it or run the call on a virtual thread and cancel it
   at the deadline.
3. Test with a stub that sends the body slowly, such as Toxiproxy and see what your client really does.

### When this is not for you

- Your client is already the JDK `HttpClient`: its read timeout is a deadline. Still budget one attempt on top of the
  retry timeout.

<a id="http-retry"></a>

## 5. When is it safe to retry?

**In short:** retry only safe calls and only short failures: at most 2 retries, with backoff and jitter, at one
layer.

```java
@Retryable(includes = { ResourceAccessException.class, HttpServerErrorException.ServiceUnavailable.class },
           maxRetries = 2, delay = 200, multiplier = 2.0, jitter = 100, maxDelay = 2000, timeout = 6000)
```

### What's going on

Retries multiply. If the gateway, your service and the payments service each retry 3 times, one click becomes
4 × 4 × 4 = 64 calls against a service that is already in trouble. Without jitter, every replica retries at the
same moment, in waves. And a 400 or a 404 will not change on the next try.

Spring Framework 7 has `@Retryable` built in but a bare one retries every exception 3 times with a fixed 1 second
delay. It also does nothing until you add `@EnableResilientMethods`: Boot 4.1 does not turn it on for you. Like
`@Transactional`, it works through a proxy, so a call from inside the same class skips it.

### Do this

1. Add `@EnableResilientMethods` to a configuration class.
2. On every `@Retryable`, set `includes`, `maxRetries` at 2 or less, `multiplier`, `jitter` and `timeout`.
3. List only short failures in `includes`: connection errors (`ResourceAccessException`), 502, 503, 504 and 429.
4. Retry at one layer only, the one closest to the failing service. Callers above it get a fast error.
5. Never retry inside a database transaction: the connection stays busy during the backoff. Call the other service
   outside the transaction.

### When this is not for you

- The provider sends `Retry-After` with 429 or 503: `@Retryable` cannot honour it. Use a `RetryTemplate` with a custom
  `BackOff` or do not retry that status.
- You already use Resilience4j for a circuit breaker: let it own the retry too. Its `max-attempts` counts the first
  call, while Spring's `maxRetries` does not.

<a id="http-idempotency"></a>

## 6. How do I retry a payment without charging it twice?

**In short:** send an idempotency key, created once per business operation, with every attempt.

### What's going on

Your call to `POST /payments` times out. Did the payment happen? You cannot know. Retry it and the customer may pay
twice.

Think of a parcel with a reference number. If you are not sure it arrived, you send it again with the same number
and the receiver throws away the copy. An idempotency key works the same way: the server stores the key with its
response and replays that response for any duplicate. The `Idempotency-Key` header is an IETF draft, not yet an
RFC, so check what your provider supports.

### Do this

1. Create the key once per business operation, for example from the order ID and the operation or a UUID stored
   with the order.
2. Create it outside the retry. Pass it as a method argument, since `@Retryable` calls again with the same
   arguments or store it so a resubmission after a pod restart reuses it.
3. Your own POST endpoints that others retry need the same: a unique constraint on the client and key and a stored
   response.
4. No key: do not retry a POST after a timeout.

### When this is not for you

- Reads and other idempotent requests: retry them without a key.

<a id="http-bulkhead"></a>

## 7. How do I stop one slow service from taking mine down?

**In short:** cap the calls to each downstream service with `@ConcurrencyLimit` and reject the rest at once. Add a
circuit breaker only when you have a concrete reason.

```java
@ConcurrencyLimit(limit = 64, policy = ConcurrencyLimit.ThrottlePolicy.REJECT)
```

### What's going on

Ships have watertight compartments, so one leak does not sink the whole ship. A concurrency limit, also called a
bulkhead, does the same for calls: when payments is slow, at most 64 of your threads wait on it and the rest of
your service keeps working.

With `policy = REJECT`, a call over the limit fails at once with `InvocationRejectedException`. The default,
`BLOCK`, waits for a free slot and with virtual threads that becomes a queue nobody sees. The limit counts per
JVM: three replicas with a limit of 64 can send 192 calls at once.

### Do this

1. Put `@ConcurrencyLimit` on the class, so all its methods share one limit. On a method, each method gets its own.
2. Always set `limit`: it has no usable default.
3. Map the rejection to a 503 or 429 for your own callers.
4. Agree on the total with the team that runs the other service.
5. For a circuit breaker or a rate limiter, use Resilience4j `resilience4j-spring-boot4` 2.4.0 with
   `spring-boot-starter-aspectj` and write down why you need it.
6. Keep fallbacks honest: a cached value or work queued for later. Never invent a result like "payment authorized".

### When this is not for you

- A dependency that fails fast at low volume: skip the circuit breaker. A few wasted calls during an outage are fine.
- A quota shared by many services: enforce it in a gateway or egress proxy, not in each replica.

<a id="http-observability"></a>

## 8. Why do some calls have no metrics or traces?

**In short:** the client was built by hand. Take clients from Boot's builders or from HTTP Service groups.

### What's going on

Boot gives an observation customizer to its `RestClient.Builder` and to every HTTP Service group. Each attempt then
produces one `http.client.requests` observation, which becomes a timer and a client span and the same step sends the
`traceparent` header so the next service joins the trace. A client made with `RestClient.create()` or
`new RestTemplate()` gets none of that: no metrics and a trace that stops at your service.

The timer's tags include `method`, `uri`, `status`, `outcome` and `client.name`. `uri` is the URI template, so a URL
built by string concatenation creates a new tag value per call. After 100 values, Boot denies new ones.

### Do this

1. Inject Boot's `RestClient.Builder` or use HTTP Service groups.
2. Use URI variables such as `{id}`, never string concatenation.
3. Turn on histograms with `management.metrics.distribution.percentiles-histogram.http.client.requests: true`.
4. Count exhausted retries from `MethodRetryEvent`, which Spring publishes for every failed attempt.

### When this is not for you

- It always applies, the first time someone asks why one call was slow.

## Put it all together

The example service makes no outbound call yet, so this section lists where each step lands instead of showing a
tested file.

### In the build

- `spring-boot-starter-restclient` for `RestClient` and HTTP Service Clients (step 1).
- `org.apache.httpcomponents.client5:httpclient5` for a pool with real limits (step 3).
- Only with a written reason: `resilience4j-spring-boot4` 2.4.0 and `spring-boot-starter-aspectj` (step 7).

### In application.yaml

- `spring.http.clients.connect-timeout` and `read-timeout`, plus `imperative.factory: http-components` (step 2).
- `spring.http.serviceclient.<group>.base-url` from an environment variable, tighter timeouts and
  `redirects: dont-follow` per group (steps 1 and 2).
- Histograms for `http.client.requests` (step 8).
- `spring.http.serviceclient.<group>.ssl.bundle` when a downstream system requires mTLS.
  [Security hardening, step 9](/guides/security/#sec-tls) explains SSL bundles and why a renewed client
  certificate needs a pod restart.

### In the code

- One configuration class with `@ImportHttpServices` per downstream system, `@EnableResilientMethods` and the pool
  customizer (steps 1, 3 and 5).
- One gateway class per downstream system, with `@ConcurrencyLimit` on the class and `@Retryable` on the methods that
  are safe to retry (steps 5 and 7).
- Idempotency keys created before the gateway call and passed in as arguments (step 6).
